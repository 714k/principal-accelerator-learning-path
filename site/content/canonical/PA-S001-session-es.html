Síntesis en 30 segundos

  1. La ingeniería de software abarca la construcción y evolución de un producto; la arquitectura examina decisiones estructurales que afectan sus propiedades y su capacidad de cambio.
  2. Distinguir una aplicación, un sistema, una plataforma y un ecosistema permite reconocer quién consume cada capacidad, dónde están las fronteras y qué contratos deben mantenerse.
  3. Una decisión Staff → Principal se justifica mediante escenarios, restricciones, alternativas y evidencia; en una plataforma frontend o un producto con IA también debe considerarse cómo comprobar el comportamiento de sus consumidores.

Al terminar la sesión, podrás delimitar una decisión de arquitectura frente a una de diseño detallado; describir una aplicación, un sistema, una plataforma y un ecosistema sin tratarlos como sinónimos; y analizar una propuesta mediante escenarios de calidad, restricciones, fronteras y contratos.

Podrás además comparar decisiones para una plataforma frontend y un producto con IA, indicando qué comportamiento necesitas evaluar y qué evidencia falta. 5. Conceptos

Staff → Principal

Ingeniería de software: disciplina de especificar, construir, probar, operar y evolucionar software bajo requisitos y restricciones

Ejemplo: un equipo modifica un servicio de reservas, prueba que el cambio respeta sus contratos y observa los errores tras desplegarlo.

Arquitectura de software: conjunto de decisiones sobre estructura, responsabilidades y relaciones de un sistema que influyen en sus propiedades importantes

Ejemplo: separar la interfaz de reservas del servicio que confirma pagos establece una frontera entre dos responsabilidades con fallos diferentes.

Diseño detallado: decisiones internas sobre cómo realiza su trabajo un componente dentro de las fronteras y contratos establecidos

Ejemplo: dentro del servicio de reservas, elegir cómo validar y representar una solicitud antes de enviarla al procesador de pagos.

Aplicación: software con una función reconocible para sus usuarios o consumidores

Ejemplo: una interfaz web permite a una persona consultar y modificar sus reservas.

Sistema: conjunto de componentes y relaciones que colaboran para ofrecer un comportamiento definido

Ejemplo: la interfaz, el servicio de reservas, la base de datos y la integración de pagos forman un sistema para gestionar reservas.

Plataforma: conjunto de capacidades compartidas, con contratos de consumo, que facilita la construcción de otros productos o aplicaciones

Ejemplo: una plataforma frontend ofrece navegación, autenticación e interfaces reutilizables a varias aplicaciones de una organización.

Ecosistema: conjunto más amplio de productos, plataformas, equipos y dependencias que interactúan, incluso cuando tienen responsables distintos

Ejemplo: una aplicación de reservas depende de una plataforma de identidad, un proveedor de pagos y herramientas de atención operadas por equipos diferentes.

Atributo de calidad: propiedad del sistema que importa a sus usuarios u operadores y que debe precisarse para poder evaluarla

Ejemplo: «el formulario debe seguir siendo utilizable con teclado» concreta una expectativa de accesibilidad que puede comprobarse.

Escenario de calidad: descripción de una situación, una respuesta esperada y una medida o criterio observable para examinar un atributo de calidad

Ejemplo: ante la caída del servicio de pagos, la interfaz informa que la reserva no se confirmó y permite reintentar sin mostrar una confirmación falsa.

Restricción: condición que limita las soluciones disponibles, con independencia de que una alternativa parezca técnicamente atractiva

Ejemplo: si una aplicación debe funcionar en navegadores admitidos por la organización, una API exclusiva de navegadores más recientes no puede adoptarse sin una alternativa.

Frontera arquitectónica: límite que asigna responsabilidades y define cómo se comunican partes de un sistema

Ejemplo: la interfaz solicita una reserva mediante una API documentada; no modifica directamente las tablas de la base de datos del servicio.

Acoplamiento: grado en que una parte depende de detalles o cambios de otra

Ejemplo: si tres aplicaciones importan archivos internos de una biblioteca, renombrar uno de esos archivos puede obligar a modificar las tres.

Cohesión: grado en que las responsabilidades de un componente contribuyen a una finalidad relacionada

Ejemplo: un módulo dedicado a gestionar reservas mantiene juntas sus reglas de confirmación y cancelación; añadirle lógica de facturación ajena dificultaría explicar su responsabilidad.

Decisión arquitectónica: elección documentable entre alternativas, tomada en un contexto de objetivos, restricciones y consecuencias

Ejemplo: un equipo elige una API compartida para consultar reservas y registra qué consumidores afecta, qué alternativa descartó y cómo comprobará la migración.

Arquitectura de Plataforma Frontend

Plataforma frontend: capacidades e interfaces compartidas que otras aplicaciones frontend utilizan para construir experiencias consistentes

Ejemplo: dos aplicaciones consumen el mismo mecanismo de navegación y componentes accesibles mediante interfaces públicas de la plataforma.

Consumidor: aplicación, equipo o componente que utiliza una capacidad ofrecida por otro componente o plataforma

Ejemplo: una aplicación de administración utiliza un componente de tabla publicado por una biblioteca compartida.

Contrato público: comportamiento, entradas y salidas que un proveedor ofrece a sus consumidores y cuyos cambios deben gestionarse explícitamente

Ejemplo: un componente de tabla acepta una lista de filas y comunica la selección mediante un evento; cambiar el nombre de ese evento afecta a sus consumidores.

Compatibilidad: capacidad de introducir un cambio manteniendo el funcionamiento esperado de los consumidores comprendidos en el alcance acordado

Ejemplo: antes de eliminar una propiedad de un componente compartido, el equipo identifica qué aplicaciones la usan y verifica que existe una ruta de migración.

Ingeniería de Producto con IA

Producto con IA: producto que incorpora una capacidad basada en IA dentro de una tarea y experiencia de usuario definidas

Ejemplo: una aplicación propone un resumen de un documento y permite a la persona revisar el texto y acceder al documento de origen.

Evaluación de IA: examen de las salidas de una capacidad de IA mediante tareas, datos y criterios explícitos; sus resultados dependen de ese diseño de evaluación

Ejemplo: para evaluar resúmenes, el equipo prepara documentos y criterios para detectar omisiones y afirmaciones sin respaldo, y revisa las salidas obtenidas.

Fallo de producto con IA: resultado o comportamiento que incumple un criterio relevante para la tarea, aunque el software haya devuelto una respuesta técnicamente válida

Ejemplo: el servicio responde correctamente a una petición, pero el resumen atribuye al documento una fecha que no aparece en él.

Contrato de interacción con IA: reglas visibles para solicitar, presentar y gestionar resultados de una capacidad de IA, incluidos sus estados de error y revisión

Ejemplo: la interfaz distingue «generando», «resultado disponible» y «no se pudo generar», y ofrece la consulta del documento original antes de que el usuario utilice el resumen.

6. Tema principal: Fundamentos de ingeniería de software y decisiones de arquitectura

Síntesis en 30 segundos

  1. La arquitectura se descubre al explicar qué decisiones estructurales afectan a varios componentes o consumidores y qué propiedad del sistema buscan proteger.
  2. Una frontera útil identifica responsables, contrato, datos, errores y forma de evolución; dibujar cajas sin estas relaciones no resuelve el problema.
  3. La evaluación compara escenarios observables y restricciones antes de elegir una opción; cuando aparece IA, comprobar que la API respondió no basta para comprobar la calidad de la respuesta.

Objetivo del tema principal

Ante un servicio hipotético de revisión documental, formular una decisión estructural, dibujar sus dependencias y contratos, predecir la propagación de un cambio y defender una alternativa con escenarios de calidad y pruebas observables. El ejercicio es un diseño hipotético no implementado: sus criterios propuestos son supuestos didácticos, no métricas medidas.

Conceptos del tema principal

Staff → Principal

Ingeniería de software: trabajo sistemático de especificar, construir, probar, operar y evolucionar software.

Ejemplo: el equipo de una aplicación documental valida un cambio del servicio antes de desplegarlo y vigila si aparecen errores.

Arquitectura de software: decisiones de estructura, fronteras y relaciones que condicionan propiedades importantes del sistema.

Ejemplo: separar identidad, documentos y generación de resúmenes delimita quién autoriza lecturas y qué servicio puede consultar contenido.

Diseño detallado: elecciones internas de un componente que implementan su responsabilidad y contrato.

Ejemplo: elegir una función que normaliza los identificadores antes de consultar un documento sin cambiar la API pública.

Escenario de calidad: situación con estímulo, entorno, respuesta y medida para comprobar un atributo de calidad.

Ejemplo: una persona sin acceso solicita un resumen; el servicio lo rechaza y una traza confirma que no invocó al proveedor de IA.

Restricción: condición que limita qué alternativas pueden adoptarse.

Ejemplo: una política hipotética exige que documentos privados permanezcan en un entorno permitido; una opción que los envíe fuera queda descartada.

Frontera arquitectónica: límite entre responsabilidades con una interfaz de interacción definida.

Ejemplo: la interfaz pide un resumen al servicio de producto; el servicio verifica acceso antes de leer el documento.

Acoplamiento: dependencia de un componente respecto de detalles de otro que puede propagar cambios.

Ejemplo: dos aplicaciones importan rutas internas del paquete de navegación y requieren cambios cuando esas rutas se mueven.

Cohesión: grado en que las responsabilidades de un componente sirven una finalidad relacionada.

Ejemplo: el módulo de acceso decide permisos de documentos; no dibuja la vista de resultados ni configura temas visuales.

Arquitectura de Plataforma Frontend

Plataforma frontend: capacidad frontend compartida ofrecida con interfaces y soporte para consumidores.

Ejemplo: dos productos usan el mismo control accesible de búsqueda mediante su API pública documentada.

Consumidor: aplicación o equipo que usa una capacidad publicada por otro.

Ejemplo: el portal documental usa la biblioteca de navegación, mientras el equipo de la biblioteca mantiene el contrato.

Contrato público: entradas, salidas, errores y comportamiento prometidos a un consumidor.

Ejemplo: un componente recibe una lista de resultados y emite el identificador del elemento elegido; el consumidor no necesita leer su estado privado.

Ingeniería de Producto con IA

Producto con IA: producto que integra una capacidad de IA dentro de una tarea y experiencia definidas.

Ejemplo: una persona solicita un resumen, revisa el documento que lo originó y puede descartar el resultado.

Evaluación de IA: examen de resultados de IA frente a tareas, datos y criterios explícitos.

Ejemplo: un conjunto de documentos de prueba se compara con criterios de omisión y atribución; la prueba registra resultados sin suponer que todos serán correctos.

Del problema a una decisión trazable

Escenario didáctico hipotético. Una organización ofrece un portal para consultar documentos y solicitar resúmenes. Hay dos aplicaciones consumidoras de controles frontend, un servicio de producto, un servicio que decide permisos, un almacén documental y un adaptador de IA. La persona usuaria quiere revisar un resumen sin recibir contenido de un documento al que no tiene acceso. Estas entidades son un modelo de enseñanza, no la arquitectura atribuida a una empresa.

La ingeniería incluye recoger el requisito, construir las piezas, probarlas, desplegarlas y operarlas. Una decisión arquitectónica aquí consiste en establecer dónde se autoriza la lectura: antes de recuperar el documento y de enviarlo a IA, dentro del servicio de producto que controla la operación. Una decisión de diseño detallado sería qué función interna usa ese servicio para validar el identificador. La distinción depende del alcance y del impacto: una función puede volverse arquitectónicamente significativa si varios servicios empiezan a depender de ella.

La página pública de ISO/IEC/IEEE 42010:2022 confirma que el estándar trata requisitos de descripción de arquitectura para diversos tipos de entidades; no asumimos cláusulas del texto completo que no se han inspeccionado. Como práctica de diseño, aquí vinculamos una preocupación de acceso con una frontera y con evidencia de prueba. ISO/IEC/IEEE 42010:2022.

Mecanismo: autorización, datos y fallos

  1. Entrada. La interfaz envía POST /documents/d7/summaries con la sesión de una persona. El identificador d7 es ficticio. La interfaz presenta «generando», pero no decide permisos por sí sola.
  2. Comprobación. El servicio de producto pide al servicio de acceso una decisión para la pareja persona/documento. Si la decisión es denegar, responde 403 y no recupera ni transmite el documento. La regla «ninguna lectura o invocación de IA tras denegación» es una invariante del diseño.
  3. Transformación. Si la decisión permite leer, el servicio obtiene el contenido autorizado y prepara la petición al adaptador de IA. El adaptador representa la integración técnica; no sustituye la evaluación del resultado ni la decisión de acceso.
  4. Salida. Si la generación termina, se devuelve un resumen con referencia al documento y un estado que obliga a revisión humana según la política hipotética del producto. El frontend muestra resultado y origen de modo distinguible.
  5. Fallo. Ante timeout del proveedor, el servicio comunica que no hay resumen disponible; la interfaz conserva la opción de consultar el documento original. Ante una salida que inventa un dato, un HTTP 200 no demuestra calidad: se requiere evaluación semántica con casos y criterios definidos.

El dibujo omite deliberadamente tiempos y proveedor concreto. Para comprobar la invariante se instrumenta el servicio con un sustituto de almacén y un adaptador de IA que registren llamadas: cuando permisos deniega, ambos deben recibir cero llamadas. Para un caso permitido, se comprueba el contrato de solicitud y el estado presentado. Estas son pruebas propuestas, no pruebas ejecutadas.

Calidad y restricciones: de adjetivos a comprobaciones

«Seguro», «rápido» y «mantenible» son objetivos demasiado generales para seleccionar entre arquitecturas. El Software Engineering Institute (SEI) propone escenarios de atributos de calidad con fuente, estímulo, entorno, artefacto, respuesta y medida. Aplicado aquí: fuente, persona sin permiso; estímulo, petición de resumen de d7; entorno, servicio disponible con una sesión válida; artefacto, flujo de resúmenes; respuesta, denegar antes de leer o enviar datos; medida, cero llamadas al almacén y adaptador en la prueba de denegación. El cero es un criterio del diseño hipotético, no una cifra de producción. SEI, Quality Attribute Workshops.

Una restricción hipotética adicional prohíbe transmitir documentos a un proveedor externo. Antes de comparar velocidad o coste, descarta cualquier alternativa que viole esa condición. Si la regla cambia o existe un proveedor permitido, se reabre la decisión. En cambio, «queremos una arquitectura moderna» no identifica un límite verificable. Los escenarios precisan qué se desea observar; las restricciones definen qué opciones son admisibles.

Fronteras, acoplamiento y cohesión

Una frontera responde quién es responsable y qué puede suponer el consumidor. El servicio de producto posee la secuencia de autorización y generación; el servicio de acceso posee la regla de permisos; el adaptador de IA posee el formato de intercambio con un proveedor. Si el frontend consulta directamente el almacén para ahorrarse una llamada, se crea otra vía que puede eludir la regla de acceso. La frontera se valida con pruebas de autorización, revisión de dependencias y observación de llamadas; no basta con poner un nombre en un diagrama.

Acoplamiento: si dos aplicaciones leen el estado privado de un componente de navegación, un cambio interno les afecta aunque el contrato público siga estable. Cohesión: si la biblioteca de navegación también decide permisos de documentos, agrupa responsabilidades que cambian por motivos distintos. Un módulo único puede ser adecuado mientras exista un solo consumidor y pocas necesidades de evolución; dividirlo prematuramente aumenta despliegues, interfaces y coordinación. La pregunta es qué cambios reales se propagan y quién puede asumir su coste.

Ejemplo resuelto: elegir dónde aplicar la autorización

Problema hipotético: se propone comprobar permisos solo en la interfaz antes de habilitar «Generar resumen». Alternativa A: esa validación visual como único control. Alternativa B: validación obligatoria en el servicio de producto antes de cualquier lectura, manteniendo la indicación visual en la interfaz para orientar al usuario.

Resolución: B mantiene la invariante aunque otra aplicación invoque la API directamente o alguien modifique la interfaz. A puede ayudar a la experiencia, pero no controla peticiones fuera de esa interfaz. El contrato observable de B es denegar sin leer ni llamar al adaptador. Prueba propuesta: simular denegación, enviar una petición directa y afirmar 403 y cero llamadas aguas abajo. Si el servicio de permisos no responde, la política de este ejemplo es no continuar la generación; hay que definir además el estado mostrado y el registro de la causa. No se ha ejecutado esta prueba ni medido latencia.

Fallos, alternativas y consecuencias de producción

  • Cambio de contrato frontend: si se renombra el evento de selección, las apps consumidoras pueden dejar de responder. Mitigación propuesta: pruebas de consumidor, versión o migración compatible y revisión de usos públicos.
  • Permisos indisponibles: no se puede asumir autorización. El diseño didáctico detiene el flujo y devuelve un error recuperable; operación real exigiría definir códigos, reintentos, telemetría y criterios de disponibilidad.
  • Contenido sensible: impedir envío previo a autorización y revisar qué datos llegan al adaptador. El diseño necesita una política de retención y tratamiento de datos que aquí no está definida.
  • Resultado de IA incorrecto: una prueba de API comprueba forma y estado; una evaluación con documentos y criterios definidos debe examinar el contenido. La revisión humana es una decisión de producto, no garantía de exactitud.
  • Separación excesiva: multiplicar servicios para un problema pequeño añade fallos de red y coordinación. Un módulo dentro de un despliegue único puede respetar las mismas fronteras lógicas y ser una alternativa válida.

Ejercicios del tema principal

  1. Clasificación. Se cambia el algoritmo privado que ordena resúmenes sin alterar entradas, salidas ni consumidores. ¿Arquitectura o diseño detallado? Respuesta: normalmente diseño detallado en el alcance dado. Si cambia una propiedad esencial, como coste o relevancia entre productos, debe reexaminarse su impacto arquitectónico.
  2. Diagnóstico. Tras denegar acceso, aparece una llamada al adaptador de IA. ¿Qué frontera falló? Respuesta: la secuencia del servicio de producto dejó pasar datos más allá de la autorización; ocultar el botón no corrige la vía directa. Aislar la petición y comprobar cero llamadas prueba la invariante.
  3. Decisión. Dos aplicaciones necesitan estados visuales iguales, pero solo una requiere un proceso de aprobación de resúmenes. ¿Qué compartir? Respuesta: es razonable compartir contratos de controles visuales pertinentes; el proceso de aprobación pertenece al dominio del producto hasta demostrar que es una capacidad común. Compartirlo por anticipado puede crear acoplamiento.

Tarjetas de estudio del tema principal

  • Pregunta: ¿qué distingue una decisión arquitectónica del diseño interno?

    Respuesta: el efecto sobre estructura, relaciones, propiedades y actores afectados; el tamaño del archivo no es el criterio.

  • Pregunta: ¿por qué «seguro» no es un escenario de calidad?

    Respuesta: no identifica estímulo, entorno, respuesta ni forma de comprobarla; «denegar antes de leer y cero llamadas posteriores» sí se puede poner a prueba.

  • Pregunta: ¿cuándo no conviene extraer una plataforma?

    Respuesta: cuando no hay consumidores y capacidades comunes suficientes para compensar el coste de contratos, soporte y evolución.

  • Pregunta: ¿un HTTP 200 valida un resumen de IA?

    Respuesta: solo informa sobre el éxito técnico de la petición según su contrato; hacen falta criterios y casos para evaluar el contenido.

    Subtema 1: Ingeniería de software, arquitectura y diseño detallado

    Síntesis en 30 segundos

    1. La ingeniería de software incluye el ciclo completo de una solución; la arquitectura y el diseño detallado son decisiones dentro de ese trabajo.
    2. La arquitectura organiza elementos, relaciones y propiedades importantes; el diseño detallado concreta cómo una parte cumple un contrato. La frontera entre ambos depende del alcance del cambio.
    3. La decisión se vuelve evaluable cuando identifica una preocupación, una alternativa, una invariante y una prueba observable.

    Objetivo del subtema 1

    Clasificar decisiones de un flujo de pagos de pedidos, explicar qué cambia cuando un consumidor llama directamente al servicio, y formular una comprobación reproducible de la regla de negocio. La demostración es hipotética, no una implementación ejecutada. El objetivo no es diseñar todavía un sistema de pagos para producción.

    Conceptos del subtema 1

    Staff → Principal
    Ingeniería de software: práctica de especificar, construir, verificar, desplegar, operar y cambiar software.

    Ejemplo: el equipo define el comportamiento de pago de un pedido, implementa el servicio, prueba el doble clic y observa los errores tras desplegarlo.

    Arquitectura de software: decisiones sobre elementos, relaciones y propiedades del conjunto que condicionan otras decisiones.

    Ejemplo: situar la autorización y el cambio de estado de pago en el servicio evita que cada cliente los interprete por separado.

    Diseño detallado: elecciones internas para implementar la responsabilidad de un elemento bajo su contrato.

    Ejemplo: una función comprueba que el identificador del pedido tenga el formato esperado antes de buscarlo; reemplazar esa función no obliga por sí mismo a cambiar a los clientes.

    Requisito: necesidad o condición que el sistema debe satisfacer para un actor o contexto.

    Ejemplo: una segunda petición del mismo intento de pago no debe confirmar dos veces el mismo pedido; esta regla guía el diseño y una prueba, aunque el protocolo concreto no está fijado aquí.

    Invariante: propiedad que debe mantenerse verdadera en todos los estados alcanzables del flujo definido.

    Ejemplo: el pedido no pasa a «pagado» si el proveedor rechaza el cargo; una prueba de rechazo confirma que conserva su estado anterior.

    Registro de decisión arquitectónica: registro del contexto, la decisión, alternativas y consecuencias que permite revisar por qué se eligió una estructura.

    Ejemplo: el equipo documenta por qué el backend posee la transición a «pagado» y qué riesgo añade la integración externa. Registrar no demuestra que la decisión sea correcta.

    Arquitectura de Plataforma Frontend
    Consumidor de contrato: aplicación que depende de la interfaz ofrecida por otra parte.

    Ejemplo: las aplicaciones web y móvil invocan la misma operación de pago del servicio; ambas reciben el estado resultante y no escriben directamente el pedido.

    Contrato público: comportamiento externo acordado para entradas, salidas, errores y estados.

    Ejemplo: POST /orders/o17/pay devuelve «pagado», «rechazado» o «pendiente» sin exponer la función interna que valida o17.

    Ingeniería de Producto con IA

    La distinción entre ingeniería, arquitectura y diseño detallado también es aplicable a un producto con IA, pero este flujo de pagos no necesita IA. No añadir un modelo al caso para llenar un carril. Como transferencia: si un producto incorpora una evaluación de resúmenes, decidir qué servicio exige la evaluación antes de publicar una salida es una frontera arquitectónica; escoger la representación interna de un caso de evaluación puede ser diseño detallado. La evaluación en sí se enseña en el subtema dedicado a IA.

    Cómo se distinguen las tres escalas

    IEEE Computer Society presenta arquitectura, diseño, construcción, pruebas, operación y mantenimiento como áreas diferentes del cuerpo de conocimiento de ingeniería de software. Es una organización del conocimiento, no una fórmula que marque automáticamente cada decisión como «arquitectura» o «detalle». El SEI vincula la arquitectura con decisiones sobre estructura y comportamiento general y con la evaluación de cualidades importantes. IEEE Computer Society, SWEBOK; SEI, Software Architecture.

    Consideremos una compra: web y móvil solicitan pagar el mismo pedido; el servicio coordina la operación y registra el estado. La ingeniería comprende acordar el requisito, implementar la funcionalidad, probar caminos normal y fallidos, desplegarla y observarla. La arquitectura decide que el servicio es el único dueño de la transición a pagado, y establece su relación con clientes, almacenamiento y proveedor. El detalle decide cómo se valida el identificador y cómo se representa internamente el resultado de esa validación.

    La clasificación no depende de que una decisión esté en un servidor, un componente grande o un archivo pequeño. Si cambiar la validación privada obliga a migrar web y móvil, quizá dejó de ser privada: hay que revisar el contrato y las dependencias reales. Si cambiar una clase interna no afecta otros elementos ni una propiedad relevante, probablemente sigue siendo diseño detallado. Este criterio de alcance es una heurística de análisis, no una cláusula que atribuyamos a un estándar.

    Mecanismo trabajado: un pedido y dos consumidores

    Datos hipotéticos: el pedido o17 inicia en PENDIENTE. Web y móvil pueden enviar POST /orders/o17/pay con un identificador de intento. El servicio debe autorizar a la persona, impedir que un mismo intento confirme dos veces y solicitar el cargo al proveedor. La forma exacta de la API, las respuestas y el proveedor son decisiones del ejemplo, no una API real citada.

    1. Entrada y contrato: el cliente envía pedido e intento. El botón puede deshabilitarse mientras espera, pero otro cliente o un reintento aún puede llamar directamente al servicio. Por eso la UI no es dueña de la regla.
    2. Comprobación: el servicio valida que la persona pueda operar el pedido y comprueba el intento registrado. Si ya existe un resultado definitivo para ese intento, devuelve el resultado conocido sin crear un segundo cargo. Una simple lectura seguida de escritura sin coordinación no demuestra esta propiedad bajo concurrencia.
    3. Dependencia externa: el servicio pide un cargo. Si el proveedor confirma, se registra la transición a PAGADO según la estrategia transaccional elegida; si rechaza, el pedido permanece sin pagar. Un timeout deja un estado incierto: no se asume éxito ni fallo definitivo sin consultar o reconciliar con el proveedor.
    4. Salida: el servicio devuelve un estado inteligible para ambos clientes. La interfaz presenta el mismo resultado sin modificar por su cuenta la fuente de verdad.

    El diagrama explica el orden conceptual, no la implementación de control de concurrencia. Para una aplicación real se necesita definir persistencia del intento, atomicidad local, tratamiento de respuestas duplicadas y reconciliación con el proveedor. Omitir estas condiciones y afirmar «idempotente» sería una garantía no demostrada.

    De la decisión al registro y a las pruebas

    Un registro de decisión para este caso podría contener: contexto, dos clientes y posible reintento; decisión, el servicio posee el estado de pago; alternativa rechazada, que la UI declare el pedido pagado; consecuencia, el servicio necesita coordinarse con almacenamiento y proveedor; riesgo abierto, timeout con resultado desconocido; evidencia necesaria, pruebas de autorización, concurrencia e integración, más un ensayo de reconciliación. Google Cloud describe los ADR como forma de conservar contexto y razones de elecciones de diseño; este registro es un ejercicio propuesto y no uno publicado por Google. Google Cloud, Architecture Decision Records.

    La prueba de unidad de la función que valida o17 cubre detalle interno. Una prueba de contrato comprueba que web y móvil interpretan correctamente estados y errores. Una prueba de concurrencia envía dos peticiones del mismo intento y verifica que solo hay un cargo y una transición final. Una prueba de fallo fuerza timeout y comprueba que el servicio no afirma PAGADO sin evidencia. Ninguna de estas pruebas fue ejecutada en este documento.

    Contraejemplos y límites

    • «Es arquitectura porque usa microservicios»: el estilo de despliegue no explica por sí solo la frontera, la propiedad protegida ni el coste. Un monolito modular podría conservar la misma responsabilidad.
    • «Es detalle porque son pocas líneas»: una línea que permite a un cliente establecer PAGADO puede violar la responsabilidad del servicio. La consecuencia importa más que la longitud.
    • «Deshabilitar el botón evita cargos duplicados»: un reintento de red o un cliente móvil puede enviar otra petición. La regla debe existir en el servicio, con almacenamiento y concurrencia adecuados.
    • «Timeout significa fracaso»: el proveedor quizá procesó el cargo antes de perderse la respuesta. Se necesita consultar o reconciliar; reintentar sin conocer el resultado puede causar un segundo cargo.
    • «Un ADR es prueba de calidad»: el documento conserva razones; el comportamiento requiere pruebas, telemetría y revisión cuando cambian supuestos.

    Ejercicios del subtema 1

    1. Clasifica y justifica. Se renombra una variable privada dentro del servicio sin cambiar comportamiento. Solución: diseño detallado o mantenimiento interno; no afecta contratos ni propiedades del sistema bajo el supuesto indicado. Si el nuevo nombre revela una regla mal entendida, revisar la regla, pero el renombre aislado no la cambia.
    2. Predice el fallo. El proveedor devuelve timeout después de recibir la petición; la UI muestra «Pago rechazado». Solución: el estado mostrado no está respaldado: el resultado del cargo es incierto. Registrar intento, consultar al proveedor o reconciliar y presentar «pendiente de confirmación». Tratarlo como éxito sería igual de injustificado.
    3. Compara estructuras. ¿Sería suficiente una biblioteca frontend compartida para garantizar un único cargo? Solución: no, porque otros clientes y reintentos pueden eludirla. Puede ayudar a presentar estados consistentes, pero el servicio debe hacer cumplir la regla con un mecanismo que resista concurrencia.

      Subtema 2: Aplicación, sistema, plataforma y ecosistema

      Síntesis en 30 segundos

      1. Una aplicación ofrece una función reconocible; un sistema reúne elementos que cooperan para producir un comportamiento; una plataforma ofrece capacidades reutilizables a consumidores; un ecosistema incluye los productos, equipos y proveedores que se afectan mutuamente.
      2. Los nombres no conceden propiedades: una biblioteca no es plataforma solo por compartirse, y varias aplicaciones no forman por sí solas un sistema integrado.
      3. La escala correcta se identifica por consumidores, contratos, ownership, operaciones y radio de cambio, no por repositorios o diagramas.

      Objetivo del subtema 2

      Delimitar las cuatro escalas en un servicio hipotético de revisión documental, identificar qué contrato pertenece a cada una y elegir dónde investigar un cambio. El escenario no describe una organización existente ni acredita un producto ejecutable.

      Conceptos del subtema 2

      Staff → Principal
      Aplicación: software con una finalidad reconocible para un grupo de personas o clientes.

      Ejemplo: un portal permite buscar documentos autorizados y solicitar un resumen.

      Sistema: elementos y relaciones que cooperan para entregar un comportamiento definido.

      Ejemplo: portal, identidad, servicio documental, almacenamiento y adaptador de IA colaboran para entregar un resumen autorizado.

      Ecosistema: red más amplia de productos, plataformas, proveedores, equipos y reglas que se influyen entre sí.

      Ejemplo: el portal depende de identidad corporativa, proveedor de IA, facturación, soporte y políticas de retención operadas por actores distintos.

      Ownership: responsabilidad identificable de mantener, decidir y responder por una capacidad o contrato.

      Ejemplo: el equipo de identidad aprueba una nueva reclamación de acceso antes de que el portal dependa de ella.

      Arquitectura de Plataforma Frontend
      Plataforma: conjunto de capacidades compartidas con usuarios o aplicaciones consumidoras, contratos y una forma de evolución.

      Ejemplo: una plataforma frontend publica navegación, autenticación visual y controles accesibles usados por tres productos.

      Capacidad de plataforma: función reutilizable que un consumidor puede descubrir, solicitar y usar mediante una interfaz definida.

      Ejemplo: un componente de búsqueda recibe resultados, anuncia cambios accesibles y emite la selección.

      Consumidor: producto, aplicación o equipo que utiliza una capacidad ofrecida por otra parte.

      Ejemplo: el portal documental usa la navegación de la plataforma sin conocer cómo está construida internamente.

      Contrato: acuerdo sobre entradas, salidas, errores, compatibilidad y expectativas de evolución entre proveedor y consumidor.

      Ejemplo: la navegación acepta rutas permitidas y emite una ruta elegida sin exponer su almacenamiento interno.

      Ingeniería de Producto con IA
      Frontera de producto con IA: límite que define qué datos, permisos, evaluación y estados se aplican antes y después de una capacidad de IA.

      Ejemplo: el servicio documental solo entrega contenido autorizado al adaptador de IA y conserva la referencia del documento en el resultado.

      Las cuatro escalas no son una jerarquía de valor

      Una aplicación puede ser esencial para el negocio sin ser plataforma. Una plataforma puede ser pequeña y solo atender a dos consumidores. Un sistema puede estar contenido en una aplicación o atravesar varias. Un ecosistema puede tener dependencias sin que un solo equipo lo controle. Las cuatro palabras responden a preguntas distintas: finalidad visible, comportamiento cooperativo, capacidad compartida y red de dependencias.

      El escenario del capítulo contiene una aplicación llamada Portal documental. Su finalidad es que una persona busque un documento que puede leer y solicite un resumen. El sistema que entrega ese resultado incluye el portal, autenticación, autorización, servicio documental, almacenamiento y adaptador de IA. La plataforma frontend proporciona navegación y controles accesibles a ese portal y a otras dos aplicaciones. El ecosistema agrega identidad corporativa, un proveedor de IA, soporte, políticas, equipos responsables y productos que dependen de la misma identidad.

      ISO describe la evaluación de arquitectura como aplicable a entidades de distintos tipos, entre ellas aplicación, sistema, producto, servicio e infraestructura. Eso respalda que deben distinguirse las entidades antes de evaluar una decisión; no establece que todo producto adopte esta taxonomía didáctica exacta. ISO/IEC/IEEE 42030:2019.

      Mecanismo: una solicitud de resumen a través de las escalas

      1. Aplicación. Una persona abre el Portal documental y selecciona resumir. La aplicación reúne interacción, contenido y estados de pantalla. No concede permiso por el hecho de ocultar o mostrar el botón.
      2. Sistema. El portal envía identidad y documento al servicio documental. El servicio solicita autorización, recupera el contenido permitido y llama al adaptador de IA. La salida vuelve como resultado o error. Cada relación requiere contrato y manejo de fallo.
      3. Plataforma. El portal consume un control de resultados de la plataforma frontend. Ese control recibe una lista, comunica selección y expone estados accesibles. Su equipo no posee la regla de acceso documental ni decide si un resumen es fiel.
      4. Ecosistema. El cambio de una reclamación de identidad puede afectar al servicio documental, a aplicaciones de auditoría y al soporte. También una política de retención puede cambiar lo permitido para el proveedor de IA. Ninguna aplicación aislada contiene por sí sola todas las decisiones ni las consecuencias.

      La imagen no declara que los elementos se desplieguen por separado. Una frontera lógica puede existir dentro de un proceso. Tampoco declara que el proveedor de IA sea parte del sistema bajo control del equipo: depende de la definición operativa que se adopte. Lo importante es documentar contratos, responsables y consecuencias de dependencia.

      Cuándo una capacidad compartida merece llamarse plataforma

      Reutilizar una carpeta, un paquete o una hoja de estilos no crea automáticamente una plataforma. Para usar ese nombre con precisión debe haber al menos consumidores identificables, capacidad útil, interfaz de uso, ownership y una forma de evolucionar cambios que afecten a esos consumidores. Si solo existe una aplicación y un import interno, suele ser código reutilizable local, no una plataforma.

      La CNCF describe una plataforma como una colección integrada de capacidades presentada según las necesidades de sus usuarios y destaca experiencias coherentes mediante portales, plantillas y APIs de autoservicio. AWS también recomienda tratar una plataforma interna como producto, con interfaz y roadmap. Estas fuentes se refieren principalmente a plataformas internas y cloud; aplicarlas a una plataforma frontend es una transferencia razonada, no la afirmación de que cualquier biblioteca de componentes satisfaga esos criterios. CNCF Platforms White Paper; AWS Prescriptive Guidance.

      Ejemplo resuelto: cambiar el contrato de identidad

      Situación hipotética: identidad va a sustituir el campo department por una lista de ámbitos de acceso. El Portal documental lo usa para mostrar secciones; el servicio documental lo usa para autorizar; una aplicación de auditoría también lo procesa.

      Clasificación: no es un cambio interno del Portal. Es un cambio de contrato dentro del ecosistema, con varios consumidores y consecuencias diferentes. El sistema documental debe definir cómo traduce ámbitos a permisos; el Portal debe manejar estados visuales; auditoría debe conservar interpretación histórica; el equipo de identidad debe publicar una migración y una fecha de retirada. Una prueba unitaria del Portal no verifica la migración completa.

      Decisión razonada: publicar ambos campos durante una transición limitada, documentar consumidores y añadir pruebas por contrato. Esto aumenta temporalmente la complejidad, pero reduce el riesgo de cambios sincronizados y silenciosos. La solución adecuada depende de cuántos consumidores haya, si se puede versionar y qué garantías permita el proveedor real.

      Fallos, límites y trade-offs

      • Confundir producto con sistema: un equipo optimiza una pantalla de resumen, pero la autorización falla en el servicio. La interfaz puede ser correcta y el comportamiento sistémico seguir siendo incorrecto.
      • Confundir paquete con plataforma: se obliga a tres aplicaciones a adoptar una biblioteca sin contrato estable ni soporte. La reutilización puede reducir duplicación al inicio, pero propaga regresiones sin un modelo de evolución.
      • Centralizar de más: convertir cada necesidad de producto en una capacidad de plataforma exige gobierno, documentación y compatibilidad. Si solo una aplicación necesita una regla de negocio, compartirla puede aumentar acoplamiento.
      • Ignorar el ecosistema: un cambio de retención de documentos afecta cumplimiento, costes, soporte y evaluación de IA aunque no cambie la interfaz. Requiere coordinación de responsables, no solo un pull request.
      • Tratar al proveedor como caja confiable: un cambio de versión, cuota o contrato puede afectar el sistema. Hacen falta límites, observabilidad y planes de recuperación; este capítulo no afirma que estén implementados.

      Ejercicios del subtema 2

Solución: es código compartido con potencial para convertirse en capacidad de plataforma, pero la evidencia dada no basta para afirmar que ya es plataforma.
      2. Traza impacto. El proveedor de identidad retira una reclamación. ¿Por qué no basta probar el Portal? Solución: porque servicio documental, auditoría y otros productos pueden consumir la reclamación. Hay que descubrir consumidores, validar contratos y planear la migración en el ecosistema.
      3. Decide dónde ubicar una regla. Solo el Portal documental requiere ocultar una etiqueta interna de clasificación. Solución: comienza como regla local de la aplicación. Convertirla en capacidad de plataforma requiere evidencia de uso común, contratos y un responsable que pueda sostenerla.

      Subtema 3: Atributos de calidad, escenarios y restricciones

      Síntesis en 30 segundos

      1. Un atributo de calidad debe describir comportamiento observable, no limitarse a un adjetivo como “rápido” o “seguro”.
      2. Un escenario define estímulo, condición, artefacto, respuesta y medida para diseñar y comprobar una propiedad.
      3. Las restricciones reducen opciones; hacerlas explícitas revela los trade-offs y evita promesas sin evidencia.

      Objetivo

      Transformarás preocupaciones vagas de rendimiento, confiabilidad, compatibilidad, accesibilidad o calidad de IA en escenarios verificables. Distinguirás meta de calidad, restricción y decisión, y pedirás evidencia antes de afirmar que una arquitectura cumple.

      Conceptos del subtema 3

      Staff → Principal
      Atributo de calidad: propiedad observable que describe cómo debe comportarse un sistema, no qué capacidad funcional ofrece.

      Ejemplo: “buscar documentos” es funcionalidad; responder con resultado útil bajo una condición y medida acordadas expresa calidad.

      Escenario de calidad: descripción de estímulo, contexto, artefacto afectado, respuesta y medida.

      Ejemplo: ante un error temporal del historial, la interfaz conserva contexto, ofrece recuperación y registra una traza consultable.

      Medida de respuesta: evidencia cuantificable o verificable que permite determinar si se alcanzó una condición.

      Ejemplo: “no debe fallar” no es comprobable; una prueba controlada que verifica recuperación y registro sí genera evidencia.

      Trade-off arquitectónico: consecuencia aceptada al privilegiar una cualidad bajo restricciones reales.

      Ejemplo: mantener una API anterior mejora compatibilidad durante migración, pero aumenta soporte temporal.

      Arquitectura de Plataforma Frontend
      Presupuesto de rendimiento: límite acordado para una medida de experiencia junto con su contexto de prueba.

      Ejemplo: una ruta inicial se mide en red y dispositivo documentados; comparar números sin contexto no demuestra experiencia de usuario.

      Compatibilidad: capacidad de cambiar una plataforma, librería o contrato sin romper el comportamiento prometido a consumidores.

      Ejemplo: retirar una propiedad puede romper aplicaciones aunque el componente se vea correcto aisladamente.

      Restricción de adopción: condición que limita cómo, cuándo o quién puede migrar una capacidad compartida.

      Ejemplo: ciclos de liberación independientes hacen inviable una migración global inmediata.

      Ingeniería de Producto con IA
      Calidad de salida: adecuación de una respuesta generada frente a relevancia, evidencia, seguridad, formato y recuperación.

      Ejemplo: una respuesta puede ser fluida y fallar si atribuye una fuente inexistente.

      Umbral de aceptación: condición que decide mostrar, revisar, degradar o bloquear una salida.

      Ejemplo: una conclusión sensible puede requerir revisión humana antes de mostrarse como definitiva.

      Conjunto de evaluación: casos, criterios y método usados para observar una capacidad de IA antes y después de cambios.

      Ejemplo: cambiar de modelo sin reevaluar casos ambiguos deja sin comprobar si la calidad requerida se conserva.

      Cómo funciona: de una cualidad vaga a una condición comprobable

      “Que sea rápido”, “que no se caiga” o “que sea accesible” son preocupaciones legítimas, pero no guían arquitectura ni pruebas. Un escenario convierte la preocupación en una cadena causal: quién inicia un evento, qué ocurre, bajo qué condición, qué artefacto responde, qué respuesta se espera y cómo se mide. El SEI documenta escenarios como herramienta para analizar si una arquitectura satisface atributos de calidad.

      1. Formula el resultado: no “hacer más rápido”, sino entregar respuesta útil o recuperación comprensible.
      2. Delimita contexto: actor, carga, red, autorización, dependencia y estado cambian la respuesta.
      3. Define contrato y estado: entrada, salida, fallo y lo que nunca debe suceder.
      4. Escoge medida y prueba: traza, contrato, carga, evaluación humana o métrica.
      5. Revisa trade-offs: una mejora de latencia puede aumentar coste, transferencia, complejidad o riesgo.

      Ejemplo trabajado: historial de documentos

      Frase insuficiente: “El historial debe cargar rápido y ser confiable”.

      Escenario hipotético de rendimiento: una persona autenticada abre su historial bajo carga definida; ruta frontend, servicio y contrato de paginación devuelven contenido útil o recuperación; se observan latencia, tasa de error y tiempo hasta contenido útil. Los valores numéricos no se fijan aquí: dependen de usuarios, riesgo, costos y evidencia operativa.

      Escenario hipotético de confiabilidad: si el servicio devuelve error temporal, el cliente conserva contexto, distingue fallo de historial vacío y ofrece recuperación. Una prueba controlada, una traza correlacionada y la inspección de estados serían evidencia posible; este documento no ejecutó esa prueba.

      Restricción a investigar: “no podemos cambiar estados de historial” podría ser contrato público, dependencia desconocida, preferencia o decisión previa costosa. Hay que identificar consumidores y fuente antes de diseñar.

      Fallos, límites y decisiones

      • Adjetivo sin escenario: “seguro” o “escalable” no define entrada, respuesta ni prueba.
      • Métrica aislada: una latencia favorable no demuestra buena interacción si la interfaz queda bloqueada.
      • Restricción sin fuente: “no se puede” debe vincularse a política, contrato, dependencia o evidencia.
      • Optimización local: reducir un paquete puede trasladar complejidad a consumidores.
      • Evaluación automática total: una mejora numérica no invalida evidencia humana de ambigüedad o falta de fundamento.

      Subtema 4: Fronteras, acoplamiento y cohesión

      Síntesis en 30 segundos

      1. Una frontera asigna responsabilidades, datos y contratos; no equivale por sí misma a una carpeta, clase o microservicio.
      2. El acoplamiento se examina por su tipo, estabilidad y costo de cambio, no solo por el número de dependencias.
      3. La cohesión ayuda a decidir qué responsabilidades deben permanecer juntas; fragmentar sin una razón de dominio, cambio u operación puede añadir complejidad.

      Objetivo del subtema 4

      Identificar fronteras útiles, analizar dependencias técnicas y organizacionales, distinguir acoplamiento perjudicial de colaboración necesaria y justificar cuándo separar o conservar juntos módulos, servicios o capacidades. Los ejemplos son hipotéticos y no describen una arquitectura implementada.

      Conceptos del subtema 4

      Staff → Principal
      Frontera arquitectónica: límite explícito que delimita responsabilidades, datos, reglas y formas permitidas de comunicación.

      Ejemplo: la interfaz solicita una cancelación mediante una API; no modifica tablas internas del servicio.

      Acoplamiento: grado y forma en que un elemento depende de otro para funcionar, cambiar, probar, desplegar u operar.

      Ejemplo: una aplicación que importa un archivo interno de una biblioteca depende de una decisión que no era parte de su contrato público.

      Cohesión: grado en que las responsabilidades de un componente pertenecen a una finalidad relacionada.

      Ejemplo: creación, confirmación y cancelación pertenecen al ciclo de vida de una reserva; reglas de nómina no.

      Contrato: comportamiento acordado que una frontera expone, con entradas, salidas, errores y reglas de evolución.

      Ejemplo: una API de cancelación define solicitud, estado de salida y qué ocurre ante un reintento.

      Dependencia temporal: relación donde una parte necesita respuesta de otra dentro de un momento específico para completar una tarea.

      Ejemplo: la interfaz no puede terminar una reserva hasta recibir confirmación del proveedor de pago.

      Dependencia de datos: relación donde un componente necesita conocer, leer o modificar datos gestionados por otro.

      Ejemplo: facturación consulta directamente tablas internas de reservas.

      Arquitectura de Plataforma Frontend
      API pública de plataforma: interfaz estable que una capacidad compartida ofrece a aplicaciones consumidoras.

      Ejemplo: un paquete de navegación expone registro de rutas sin revelar cómo almacena el historial.

      Compatibilidad hacia atrás: capacidad de evolucionar un contrato sin romper el comportamiento acordado de consumidores existentes.

      Ejemplo: un componente añade una propiedad opcional sin eliminar ni reinterpretar las anteriores.

      Acoplamiento por versión: dependencia entre un consumidor y una versión concreta de un contrato o biblioteca.

      Ejemplo: una aplicación necesita migrar antes de adoptar una versión que elimina una propiedad.

      Ingeniería de Producto con IA
      Frontera de evidencia: separación entre contenido fuente, transformación de IA y afirmación presentada a la persona usuaria.

      Ejemplo: un resumen conserva referencias al documento que respalda cada afirmación relevante.

      Acoplamiento semántico: dependencia de significado que puede romperse aunque la estructura técnica siga funcionando.

      Ejemplo: un estado approved se interpreta como revisión legal cuando solo indica formato válido.

      Una frontera no es una división mecánica

      Una frontera puede existir dentro de un monolito, entre módulos de frontend, entre aplicaciones o entre servicios. Es útil si permite identificar quién posee una regla, qué datos puede modificar directamente cada parte, qué contrato deben usar los demás y qué cambio debería poder ocurrir sin coordinar a todos los consumidores. El Software Engineering Institute describe el acoplamiento como el grado de dependencia entre componentes y la cohesión como el grado en que las partes de un módulo pertenecen juntas. SEI: coupling and cohesion.

      Las dependencias no son un defecto por sí mismas. El riesgo aumenta si exponen detalles que deberían permanecer internos, exigen cambios simultáneos innecesarios o impiden probar, desplegar o recuperar partes de forma independiente.

      Mecanismo: cambio local frente a regresión sistémica

      En este modelo, una plataforma frontend ofrece un componente de estado a dos aplicaciones. El servicio de solicitudes conserva el ciclo de vida y almacenamiento. Las aplicaciones consumen un contrato público, no las tablas ni detalles internos.

      Si el servicio cambia su valor interno de in_review a otro formato, las aplicaciones no deberían cambiar si el contrato público conserva la misma semántica. En cambio, si una aplicación consulta el almacenamiento directamente, aparece acoplamiento de datos: un detalle interno pasa a requerir coordinación entre equipos.

      • Reutilización forzada: una lógica local no debe centralizarse sin consumidores, contrato y ownership sostenibles.

La plataforma representa estados, citas y acciones accesibles. El componente no decide si una respuesta es jurídicamente correcta ni qué contenido puede enviarse al proveedor.

      Cómo evoluciona un contrato

      Un cambio compatible puede añadir una propiedad opcional sin alterar valores previos ni su significado. Renombrar un evento, eliminar una propiedad o reinterpretar un estado es incompatible. npm recomienda una versión mayor para cambios que rompen compatibilidad, una menor para nuevas capacidades compatibles y parche para correcciones compatibles. npm: semantic versioning.

      1. Descubrir consumidores: identificar aplicaciones, equipos, versiones y usos reales.
      2. Clasificar el cambio: distinguir cambios estructurales, semánticos, de accesibilidad, rendimiento y seguridad.
      3. Diseñar transición: mantener contrato previo temporalmente, publicar adaptador o guía de migración.
      4. Probar proveedor y consumidores: la plataforma prueba contrato; el producto prueba su integración.
      5. Observar adopción: registrar errores, advertencias de deprecación y solicitudes de soporte.
      6. Retirar con evidencia: eliminar solo tras migración o decisión explícita sobre consumidores restantes.

      Accesibilidad como contrato de plataforma

      La plataforma debe garantizar semántica apropiada, teclado, foco, estados comprensibles y contraste en capacidades comunes. El consumidor debe aportar etiquetas, contenido, orden de flujo y manejo de errores propio. W3C advierte que widgets personalizados requieren que sus autores proporcionen soporte de teclado y gestionen foco; los elementos HTML nativos ya aportan parte de ese comportamiento. W3C: Developing a Keyboard Interface.

      Fallos, límites y trade-offs

      • Centralizar todo: una plataforma que absorbe reglas particulares de producto pierde cohesión y se vuelve cuello de botella.
      • Tipos como único contrato: tipos no prueban semántica, foco, contraste, rendimiento ni significado de estados.
      • Opciones ilimitadas: cada propiedad pública multiplica superficie de compatibilidad y combinaciones de prueba.
      • Sin migración: una versión mayor sin inventario y guía traslada riesgo a consumidores.
      • Componente accesible con contenido inaccesible: foco correcto no compensa instrucciones ambiguas, errores inexplicables o acciones irreversibles.

      Resumen en 30 segundos

      1. Clasifica una decisión por impacto, reversibilidad, riesgo, dependencias y evidencia; no por jerarquía.

      Staff → Principal, Arquitectura de Plataforma Frontend e Ingeniería de Producto con IA son perspectivas sobre el mismo sistema: una define alcance, riesgo y propiedad; otra convierte decisiones repetibles en contratos y adopción; la tercera verifica que la salida de IA sea adecuada, observable y recuperable.

      1. Una capacidad compartida necesita frontera, contrato, consumidores, propiedad y evolución explícitos.

      Conceptos de integración

      Staff → Principal

      Frontera de decisión: límite entre una decisión local y una que afecta contratos, consumidores, riesgo o coste compartido.

      Ejemplo: cambiar texto es local; cambiar el significado de “aprobado” en tres productos requiere coordinación transversal.

      Propiedad sostenible: responsabilidad explícita de mantener contrato, soporte, evolución y retiro de una capacidad.

      Ejemplo: una librería sin responsable de compatibilidad y soporte es dependencia compartida, no plataforma sostenible.

      Riesgo transferido: riesgo que un equipo evita localmente pero desplaza a consumidores, operación o personas usuarias.

      Ejemplo: retirar una propiedad sin migración reduce mantenimiento local y puede bloquear liberaciones de consumidores.

      Arquitectura de Plataforma Frontend

      Contrato transversal: comportamiento compartido con entradas, salidas, errores, compatibilidad y responsabilidad de evolución definidos.

      Ejemplo: los estados “generando”, “disponible”, “requiere revisión” y “no disponible” deben conservar significado entre consumidores.

      Ruta de adopción: secuencia que permite incorporar una capacidad sin interrupción indebida.

      Ejemplo: publicar versión, documentar diferencias, mantener compatibilidad temporal y medir consumidores restantes.

      Observabilidad compartida: señales comunes para conocer comportamiento de una capacidad a través de productos consumidores.

      Ejemplo: eventos consistentes permiten comparar errores, adopción y necesidad de recuperación.

      Ingeniería de Producto con IA

      Contrato de interacción con IA: reglas para solicitar, presentar, revisar y recuperar resultados generados.

      Ejemplo: una respuesta no se presenta como confirmada si no puede mostrar evidencia, estado de revisión o limitación.

      Evaluación continua: observación repetida del comportamiento tras cambios de modelo, datos, interfaz o política.

      Ejemplo: al cambiar modelo se revisan casos críticos, ambigüedad, evidencia y recuperación, no solo una métrica automática.

      Supervisión humana: participación definida cuando el riesgo o impacto supera el umbral aceptable para automatización.

      Ejemplo: una sugerencia de bajo impacto puede mostrarse; una conclusión sensible puede requerir revisión antes de una acción.

      La secuencia práctica es: partir de la tarea y su riesgo; separar lo específico de producto de lo común; definir contrato y estados; establecer evaluación y observabilidad; asignar propiedad y ruta de adopción; revisar con evidencia.       Separar superficies

      Una tarjeta de concepto reusable debe definir entrada, salida semántica, estados, alternativa sin JavaScript, compatibilidad y método de verificación. Copiar diez tarjetas visualmente similares no demuestra una abstracción estable.

      4. Construir el mínimo verificable.
      5. Probar comportamiento, teclado, toque y alternativa sin JavaScript cuando aplique.
      6. Registrar resultado, trade-off y condición de revisión.

      9. Ejemplo del mundo real: reintentos y estados de pago documentados por Stripe

      Hechos documentados. La API v1 de Stripe acepta claves de idempotencia en solicitudes POST; después de comenzar la ejecución conserva código y cuerpo de la primera respuesta para la misma clave, incluso un error 500. Compara los parámetros de un reintento con los originales y puede eliminar claves después de al menos 24 horas. Una validación fallida antes de ejecutar el endpoint no guarda ese resultado. Esta descripción procede de su referencia de solicitudes idempotentes; no describe un despliegue concreto de un comercio.

      Stripe documenta que un PaymentIntent sigue estados durante el proceso de pago y que una integración lo crea y confirma; normalmente corresponde a un carrito o sesión de cliente. Su guía actual recomienda Checkout Sessions para la mayoría de integraciones y reserva Payment Intents para casos que requieren mayor control. Esta lección usa PaymentIntents para analizar la frontera y los estados, sin recomendarlo como elección predeterminada. Fuente: guía Payment Intents de Stripe.

      Stripe también documenta webhooks para reaccionar a eventos asíncronos como confirmaciones bancarias. En una arquitectura que promete confirmar un pedido, la página de regreso del navegador por sí sola no sería evidencia suficiente de que el pago quedó asentado: ésta es una inferencia de diseño a partir de la asincronía documentada, no un resultado medido por Stripe. Fuente: guía de webhooks.

      Mecanismo y límite: reutilizar una clave para el mismo intento ayuda a evitar repetir una operación en la API v1 dentro de las condiciones documentadas; cambiar parámetros produce error, reutilizar una clave expirada puede producir una nueva operación y un 500 guardado no prueba el resultado final del negocio. El servidor propio todavía necesita su autorización, relación pedido-intento, almacenamiento y conciliación. Ninguna fuente citada demuestra aquí una tasa de éxito, el código de un comerciante ni una garantía transaccional entre ambos sistemas.

      Decisión Staff/Principal: un equipo que comparte un flujo entre web y móvil necesita asignar dueño al estado del pedido y documentar qué prueba refuta la hipótesis «un reintento es seguro». La decisión de qué producto de Stripe usar depende de los requisitos y de la guía vigente; no se deduce del diagrama.

      Requisitos, contratos y estados

      La persona autenticada puede iniciar un intento de pago del pedido que le pertenece. El pedido tiene un importe calculado en servidor y estados PENDIENTE, EN_PROCESO, PAGADO, RECHAZADO y REVISION. Sólo una confirmación sustentada por la fuente de pagos lleva a PAGADO; un timeout lleva a consulta o reconciliación. No se envían claves secretas al navegador. Se debe documentar en qué regiones, medios y reglas de negocio aplica este diseño.

      Contrato propuesto, no desplegado
      Operación Entrada Salida y error
      POST /orders/{id}/payment-attempts Identidad autenticada y attemptId opaco; importe tomado del servidor. 202 EN_PROCESO + identificador de seguimiento; 403 sin permiso; 409 si intento incompatible.
      GET /orders/{id}/payment Pedido propio. Estado y fecha de actualización; 404 o respuesta de privacidad coherente con la política de acceso.
      POST /payment-events Evento firmado del proveedor. 2xx tras registrar/encolar de forma durable; rechazar firma inválida.

      El servidor valida identidad y pertenencia antes de leer o escribir intentos. Un índice único compuesto por pedido e intento impide dos registros locales para el mismo intento. Una transacción local actualiza el intento y el estado del pedido; no implica transacción distribuida con el proveedor. El receptor verifica firma sobre el cuerpo original y registra identificador de evento procesado para evitar aplicar dos veces un evento repetido. La secuencia de entrega puede variar: comparar estado/versiones y reconciliar antes de aplicar una transición tardía.

      Algoritmo esencial propuesto

      async function startPayment(user, orderId, attemptId) {
  const order = await orders.getAuthorized(orderId, user.id);
  if (!order) return { status: 403 };
  const attempt = await attempts.insertOrGetUnique(order.id, attemptId);
  if (attempt.final) return attempt.publicResult;
  await queue.enqueueOnce(attempt.id, { orderId: order.id });
  return { status: 202, body: { attemptId, state: "EN_PROCESO" } };
}

      El pseudocódigo no garantiza por sí solo atomicidad entre la inserción y la cola; una implementación debe usar una salida transaccional, reexploración durable o una tecnología equivalente y demostrar el comportamiento bajo caída del proceso. El trabajador construye la clave idempotente sin datos personales, conserva una relación durable con el resultado externo y no crea una nueva clave ante un mero reintento del mismo intento. La guía Stripe documenta límites para las claves v1; por eso la aplicación conserva su propia reconciliación. Referencia de Stripe.

      Seguridad, experiencia y operación

      El navegador sólo ve estado y un identificador opaco, con botón etiquetado y mensajes anunciados en aria-live; ofrece espera, error recuperable y acceso al estado confirmado. No confiar en importe ni permiso suministrado por cliente. Registrar correlación pedido-intento-evento con datos minimizados, latencia y errores por transición, y alertar por acumulación de REVISION. Nunca incluir claves, detalles de pago ni texto privado en logs públicos.

      Desplegar primero detrás de una bandera para una cohorte de prueba, migrar datos con posibilidad de leer estados anteriores, ejecutar pruebas de contrato de web y móvil y preparar rollback que detenga nuevos intentos sin borrar eventos pendientes. Un rollback de interfaz no revierte cargos: el plan operativo requiere conciliación. Probar autorización, doble clic, dos clientes concurrentes, caída tras encolar, evento duplicado/fuera de orden, clave vencida, rechazo, timeout, lectura con teclado y vista sin JavaScript. Resultado de todas estas pruebas: pendiente.

      12. Ejercicios

      1. Comprensión. Una aplicación web usa un servicio y una biblioteca compartida. Dibuja las tres fronteras y di qué cambio interno puede quedar invisible. Solución: web → interfaz pública de biblioteca, web → API de servicio y servicio → persistencia. Reemplazar una función privada que preserva contrato y propiedades observables puede quedar invisible; cambiar el evento público no.
      2. Decisión. Dos equipos quieren compartir una función de resumen de IA; sólo uno ha definido criterios de error. Compara compartir proveedor, compartir contrato y mantener dos implementaciones. Solución: primero definir tarea, autorización, salidas y evaluación común; sin ello compartir proveedor no demuestra plataforma. Un contrato común puede preceder a una implementación compartida; mantener soluciones locales permite aprender pero duplica trabajo. Registrar supuestos y condición de revisión.
      3. Implementación propuesta. Especifica una prueba para un intento de pago duplicado. Solución: preparar pedido pendiente, usuario autorizado y mismo intento; enviar dos peticiones concurrentes; verificar un registro de intento, una operación externa según el doble o sandbox y estado coherente. Repetir con clave distinta y mismo pedido para descubrir otra política de negocio; no inferir idempotencia sólo del doble clic.
      4. Diagnóstico. Un timeout devuelve un error al cliente mientras el proveedor procesó la operación. ¿Qué estado puede mostrarse? Solución: pendiente de comprobación; consultar fuente externa, procesar eventos y conciliar. Decir «rechazado» o «pagado» sin respuesta fiable confunde transporte con negocio.
      5. Liderazgo. Un cambio de un contrato compartido afecta web, móvil y un equipo de IA. Redacta una decisión con alternativa, responsable y evidencia. Solución orientativa: conservar versión anterior durante migración; cada dueño prueba su consumidor; responsable de contrato coordina fechas, señales de error y rollback. La decisión debe explicitar coste y revisión, no deducir jerarquía de títulos.

      Evaluación: una respuesta sólida nombra actores, frontera, entrada y salida, fallo alternativo, supuesto decisivo y prueba que podría refutarla. Las soluciones son modelos razonados, no resultados ejecutados.

Synthesis in 30 seconds

  1. Software engineering covers the construction and evolution of a product; Architecture examines structural decisions that affect its properties and its ability to change.
  2. Distinguishing an application, a system, a platform and an ecosystem allows us to recognize who consumes each capacity, where the boundaries are and what contracts must be maintained.
  3. A Staff → Principal decision is justified by scenarios, constraints, alternatives and evidence; In a frontend platform or a product with AI, how to check the behavior of your consumers should also be considered.

5. Concepts

Staff → Principal

Software engineering: discipline of specifying, building, testing, operating and evolving software under requirements and constraints

Example: a team modifies a reservation service, tests that the change respects its contracts and observes errors after deploying it.

Software architecture: set of decisions about the structure, responsibilities and relationships of a system that influence its properties important

Example: separating the reservations interface from the service that confirms payments establishes a boundary between two responsibilities with different failures.

Detailed design: internal decisions about how a component performs its work within established boundaries and contracts

Example: within the service of reservations, choose how to validate and represent a request before sending it to the payment processor.

Application: software with a function recognizable to its users or consumers

Example: a web interface allows a person to consult and modify their reservations.

System: set of components and relationships that collaborate to provide defined behavior

Example: the interface, reservation service, database and payment integration form a system to manage reservations.

Platform: set of shared capabilities, with consumer contracts, that makes it easy to build other products or applications

Example: a platform Frontend provides navigation, authentication, and reusable interfaces to multiple applications in an organization.

Ecosystem: broader set of products, platforms, teams and dependencies that interact, even when they have owners different

Example: a booking application depends on an identity platform, a payment provider and service tools operated by different teams.

Quality attribute: property of the system that matters to its users or operators and that must be specified in order to be evaluated

Example: “the form must remain usable with a keyboard” specifies a verifiable accessibility expectation.

Quality scenario: description of a situation, an expected response and an observable measure or criterion to examine a quality attribute

Example: when the payment service fails, the interface reports that the reservation was not confirmed and allows retry without displaying a false confirmation.

Restriction: condition that limits the available solutions, regardless of whether an alternative appears technically attractive

Example: If an application must work in browsers supported by the organization, an API exclusive to newer browsers cannot be adopted without an alternative.

Architectural boundary: boundary that assigns responsibilities and defines how parts of a system communicate

Example: interface requests a reservation using a documented API; does not directly modify the service's database tables.

Coupling: degree to which one part depends on details or changes of another

Example: If three applications import files internal to a library, renaming one of those files may require modification of all three.

Cohesion: degree to which a component's responsibilities contribute to a related purpose

Example: a module dedicated to managing reservations keeps its confirmation and cancellation rules together; Adding extraneous billing logic would make it difficult to explain your responsibility.

Architectural decision: documentable choice between alternatives, taken in a context of objectives, constraints and consequences

Example: a team chooses a shared API to query reservations and records which consumers it affects, which alternative it ruled out, and how it will check the migration.

Platform Architecture Frontend

Frontend platform:shared capabilities and interfaces that other frontend applications use to build experiences consistent

Example: two applications consume the same navigation mechanism and components accessible through public interfaces of the platform.

Consumer: application, computer, or component that uses a capability offered by another component or platform

Example: a management application uses a table component published by a shared library.

Public contract: behavior, inputs and outputs that a provider offers to its consumers and whose changes must be managed explicitly

Example: a table component accepts a list of rows and communicates the selection using an event; changing the name of that event affects its consumers.

Compatibility:ability to make a change while maintaining the expected performance of consumers within the agreed scope

Example: Before removing a property from a shared component, the team identifies which applications use it and verifies that a migration path exists.

Product Engineering with AI

AI product: product that incorporates an AI-based capability within a defined task and user experience

Example: an application proposes a summary of a document and allows the person to review the text and access the source document.

AI evaluation: examination of the outputs of an AI capability using explicit tasks, data, and criteria; its results depend on that evaluation design

Example: To evaluate summaries, the team prepares documents and criteria to detect omissions and unsupported statements, and reviews the outputs obtained.

AI product failure: result or behavior that violates a criterion relevant to the task, even though the software returned a technically valid response

Example: the service responds correctly to a request, but the summary attributes a date to the document that does not appear in it.

Interaction contract with AI: Visible rules for requesting, presenting, and managing results from an AI capability, including their error and review statuses

Example: The interface distinguishes “generating,” “result available,” and “could not be generated,” and provides viewing of the original document before the user uses the summary.

From the problem to a traceable decision

Hypothetical teaching scenario. An organization offers a portal to view documents and request summaries. There are two applications that consume frontend controls, a product service, a service that decides permissions, a document store and an AI adapter. The user wants to review a summary without receiving content from a document to which they do not have access. These entities are a teaching model, not the architecture attributed to a company.

Engineering includes collecting the requirement, building the parts, testing them, deploying them and operating them. An architectural decision here is to establish where the read is authorized: before retrieving the document and sending it to IA, within the product service that controls the operation. A detailed design decision would be which internal function that service uses to validate the identifier. The distinction depends on scope and impact: a feature can become architecturally significant if multiple services begin to depend on it.

The public page for ISO/IEC/IEEE 42010:2022 confirms that the standard addresses architectural description requirements for various types of entities; We do not assume full text clauses that have not been inspected. Mechanism: authorization, data and faults

  1. Input. The interface sends POST /documents/d7/summaries with a person's session. The identifier d7 is fictitious. The interface presents "generating", but does not decide permissions on its own.
  2. Checking. The product service asks the access service for a decision for the person/document pair. If the decision is to deny, respond 403 and do not retrieve or transmit the document. The “no read or AI invocation upon denial” rule is a design invariant.
  3. Transformation. If the decision allows read, the service obtains the authorized content and prepares the request to the AI ​​adapter. The adapter represents technical integration; it does not replace the evaluation of the result or the access decision.
  4. Exit. If the generation ends, a summary is returned with reference to the document and a status that requires human review according to the hypothetical policy of the product. The frontend shows result and origin in a distinguishable way.
  5. Failure. Upon provider timeout, the service communicates that there is no summary available; The interface retains the option to consult the original document. When faced with an output that invents data, an HTTP 200 does not demonstrate quality: semantic evaluation with defined cases and criteria is required.

The drawing deliberately omits specific times and supplier. To test the invariant, the service is instrumented with a store surrogate and an AI adapter that log calls: when permissions are denied, both should receive zero calls. For a permitted case, the application contract and the submitted status are checked. These are proposed tests, not executed tests.

Quality and constraints: from adjectives to checks

“Secure,” “fast,” and “maintainable” are too general goals for selecting between architectures. The Software Engineering Institute (SEI) proposes quality attribute scenarios with source, stimulus, environment, artifact, response and measurement. Applied here: source, person without permission; stimulus, summary request for d7; environment, service available with a valid session; artifact, abstract stream; response, deny before reading or sending data; measure, zero calls to the store and adapter in the denial test. Zero is a hypothetical design criterion, not a production figure. SEI, Quality Attribute Workshops.

An additional hypothetical restriction prohibits transmitting documents to an external provider. Before comparing speed or cost, rule out any alternative that violates that condition. If the rule changes or a permitted provider exists, the decision is reopened. On the other hand, “we want modern architecture” does not identify a verifiable limit. The scenarios specify what you want to observe; constraints define which options are admissible.

Boundaries, coupling and cohesion

A border answers who is responsible and what the consumer can assume. The product service has the authorization and generation sequence; the access service owns the permissions rule; The AI ​​adapter is formatted for exchange with a provider. If the frontend queries the store directly to save a call, another path is created that can bypass the access rule. The border is validated with authorization tests, review of dependencies and observation of calls; It is not enough to put a name in a diagram.

Coupling: If two applications read the private state of a navigation component, an internal change affects them even if the public contract remains stable. Cohesion: If the navigation library also decides document permissions, it groups together responsibilities that change for different reasons. A single module may be adequate as long as there is a single consumer and few evolution needs; splitting it prematurely increases deployments, interfaces and coordination. The question is what real changes are propagated and who can bear their cost.

Solved example: choosing where to apply authorization

Hypothetical problem: It is proposed to check permissions only in the interface before enabling “Generate summary”. Alternative A: that visual validation as the only control. Alternative B: mandatory validation in the product service before any reading, maintaining the visual indication in the interface to guide the user.

Resolution: B maintains the invariant even if another application invokes the API directly or someone modifies the interface. A can help the experience, but it doesn't handle requests outside of that interface. B's observable contract is to deny without reading or calling the adapter. Proposed test: simulate denial, send a direct request and assert 403 and zero downstream calls. If the permissions service is not responding, the policy in this example is not to continue the build; You must also define the displayed status and the cause record. This test has not been run or latency measured.

Faults, alternatives and production consequences

  • Fronend contract change: If the selection event is renamed, consuming apps may stop responding. Proposed mitigation: consumer testing, supported version or migration, and public usage review.
  • Unavailable permissions: authorization cannot be assumed. The instructional design stops the flow and returns a recoverable error; Actual operation would require defining codes, retries, telemetry and availability criteria.
  • Sensitive content: prevent sending prior to authorization and review what data reaches the adapter. The design requires a data retention and processing policy that is not defined here.
  • Incorrect AI result: an API test checks form and state; an evaluation with defined documents and criteria must examine the content. Human review is a product decision, not a guarantee of accuracy.
  • Excessive separation: multiplying services for a small problem adds network failures and coordination. A module within a single deployment can respect the same logical boundaries and be a valid alternative.

    How the three scales are distinguished

    IEEE Computer Society presents architecture, design, construction, testing, operation, and maintenance as distinct areas of the software engineering body of knowledge. It is a knowledge organization, not a formula that automatically marks each decision as “architecture” or “detail.” The SEI links architecture to decisions about overall structure and behavior and to the evaluation of important qualities. IEEE Computer Society, SWEBOK; SEI, Software Architecture.

    Let's consider a purchase: web and mobile ask to pay for the same order; the service coordinates the operation and records the status. Engineering involves agreeing the requirement, implementing the functionality, testing normal and failed paths, deploying it and observing it. The architecture decides that the service is the sole owner of the transition to paid, and establishes its relationship with clients, storage and provider. The detail decides how the identifier is validated and how the result of that validation is represented internally.

    Classification does not depend on whether a decision is on a server, a large component, or a small file. If changing private validation requires migrating web and mobile, perhaps it is no longer private: the contract and real dependencies must be reviewed. If changing an inner class doesn't affect other elements or a relevant property, it's probably still fine-grained design. This scope criterion is aanalysis heuristics, not a clause that we attribute to a standard.

    Counterexamples and limits

    • “It is architecture because it uses microservices”: the deployment style alone does not explain the boundary, the protected property or the cost. A modular monolith could retain the same responsibility.
    • “It is a detail because there are few lines”: a line that allows a client to establish PAGADO may violate the responsibility of the service. Consequence matters more than length.
    • “Disabling the button prevents duplicate charges”: a network retry or a mobile client can send another request. The rule must exist in the service, with adequate storage and concurrency.
    • “Timeout means failure”: the provider may have processed the charge before missing the response. Consultation or reconciliation is needed; retrying without knowing the result may cause a second charge.
    • “An ADR is proof of quality”: the document retains reasons; behavior requires testing, telemetry, and review when assumptions change.

      Synthesis in 30 seconds

      Subtopic 7

      Decisions and responsibilities Staff → Principal

      The scope of a decision is not deduced from the title of the person proposing it. It is deduced from its radius of impact, reversibility, risks, dependencies and available evidence.

      Summary in 30 seconds

      1. Classifies a decision by impact, reversibility, risk, dependencies and evidence; not by hierarchy.
      2. Staff and Principal make alternatives, boundaries, consequences and responsible parties visible; they do not replace those who own the domain, the platform, security or operation.
      3. A defensible decision leaves context, options, restrictions, consequences, responsible parties, evidence and explicit review conditions.

      Objective

      At the end you will be able to classify the scope and reversibility of a decision, gather the necessary people without turning the process into infinite consensus, compare alternatives with proportional evidence and record what was decided, who executes each part and what signal would force it to be reviewed.

      Concepts by professional field

      Staff → Principal
      Architectural decision
      Choice between alternatives that modifies the structure, quality attributes, limits or evolution of the system. Example: publish a versioned API so that three products consume the same state.
      Decision context
      Business, technical, operational and restrictions information that makes the choice intelligible. Example: three products display AI citations in incompatible ways.
      Alternative
      Viable option that solves the problem with its own costs and consequences: solve locally, create a library, offer a platform capability, or buy a service.
      Trade-off
      Accepted consequence when choosing an option. Example: a temporary migration costs time now, but reduces the risk of breaking consumers later.
      Reversibility
      Cost, time and risk of undoing a decision. Changing text is usually reversible; withdrawing a public contract rarely is.
      Radius of impact
      People, products, contracts, data and operations affected. An identity decision can cross many boundaries even if it changes only a few lines of code.
      Architectural risk
      A condition that can prevent a relevant objective. Example: adopt an AI capability without having tested its behavior in critical cases.
      Frontend Platform Architecture
      Contract governance
      Ability to publish, version, deprecate and withdraw a contract without surprising those who depend on it him.
      Shared responsibility
      Explicit distribution of obligations: the platform maintains compatibility and documentation; the consumer integrates, tests and migrates within the agreed timeframe.
      Standardization decision
      Choice to extract a repeat solution when there is a stable problem, multiple consumers and a sustainable property.
      AI Product Engineering
      Risk threshold
      Rule that defines when review, block or recover an experience. Example: an answer without evidence must be presented as unverified and offer recovery.
      Evaluation manager
      Person or team that defines quality criteria, evidence and monitoring; is not necessarily the one who implements the model.
      Critical assumption
      A statement not yet proven that would change the decision if it turned out to be false. Example: that all consumers of an API can be identified and migrated in six weeks.

      There is no universal matrix that automatically converts a decision to “Staff” or “Main”. The following template is a guide for discussing outreach; formal authority and actual limits depend on the organization.

      The mechanism in six moves
      1. Formulates the problem, not the solution. “AI quotes are inconsistent between products” allows alternatives; “we need a global component” already restricts them.

      5. Records the decision and its consequences. An ADR is not a minute: it preserves why it was chosen, what was discarded, who owns the execution, and what debt remains.
      6. Execute, observe, and review. Defines signal, date, or review condition. Documenting does not eliminate the need to learn in production.

It must be documented in which regions, media and business rules this design applies.

      Essential algorithm proposed

      async function startPayment(user, orderId, attemptId) {
  const order = await orders.getAuthorized(orderId, user.id);
  if (!order) return { status: 403 };
  const attempt = await attempts.insertOrGetUnique(order.id, attemptId);
  if (attempt.final) return attempt.publicResult;
  await queue.enqueueOnce(attempt.id, { orderId: order.id });
  return { status: 202, body: { attemptId, state: "EN_PROCESO" } };
}

      Pseudocode alone does not guarantee atomicity between the insert and the queue; An implementation must use transactional exit, durable rescan, or equivalent technology and demonstrate behavior under process crash. The worker constructs the idempotent key without personal data, maintains a durable relationship with the external result, and does not create a new key upon a mere retry of the same attempt.       Security, experience and operation

      Browser only sees status and an opaque identifier, with labeled button and messages announced inaria-live; offers wait, recoverable error and access to committed state. Do not trust the amount or permission provided by the client. Record order-attempt-event correlation with minimized data, latency and errors per transition, and alert due to accumulation of REVISION. Never include keys, payment details or private text in public logs.

      12. Exercises

      1. Comprehension. A web application uses a service and a shared library. Draw the three boundaries and say what internal change can remain invisible. Solution: web → library public interface, web → service API and service → persistence. Overriding a private function that preserves contract and observable properties can become invisible; change public event no.
      2. Decision. Two teams want to share an AI summary function; only one has defined error criteria. Compare provider sharing, contract sharing, and maintaining two implementations. Solution: first define task, authorization, outputs and common evaluation; Without this, sharing a provider does not prove a platform. A common contract may precede a shared implementation; Maintaining local solutions allows learning but duplicates work. Record assumptions and review condition.
      3. Proposed implementation. Specifies a test for a duplicate payment attempt. Solution: prepare pending order, authorized user and same attempt; send two concurrent requests; verify an attempt record, an external operation according to the double or sandbox and consistent state. Repeat with a different key and same order to discover another business policy; do not infer idempotence only from the double click.
      4. Diagnosis. A timeout returns an error to the client while the provider processed the operation. What status can be displayed? Solution: pending verification; consult external source, process events and reconcile. Saying “rejected” or “paid” without a reliable answer confuses transportation with business.
      5. Leadership. A change to a shared contract affects web, mobile, and an AI team. Write a decision with alternative, responsible party and evidence. Guidative solution: keep previous version during migration; each owner tests his consumer; Contract manager coordinates dates, error signals and rollback. The decision must explain cost and review, not deduce hierarchy of titles.

      Evaluation: a solid answer names actors, border, entry and exit, alternative failure, decisive assumption and evidence that could refute it. Solutions are reasoned models, not executed results.

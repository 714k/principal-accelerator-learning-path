3. Synthesis in 30 seconds

  1. Code placement and dependency boundaries are different decisions.
  2. A graph allows reasoning about impact only if it represents the relevant relationships.
  3. Sustainable standards need detector, owner, exception, and evidence.

4. Objective

When finished, you will draw a graph of applications and packages with public APIs; you will distinguish monorepo from polyrepo under real restrictions; you will derive affected tasks; you will design a positive and a negative boundary test; and you will justify the adoption of a gate without attributing properties that it does not measure.

5. Learning Preview

Staff → Principal

Decide borders and standards, assign ownership, resolve exceptions and plan migration with review criteria.

Frontend Platform Architecture

Distinguish application, workspace and package; expose public entry points; read project and task graphs, and keep builds reproducible.

Product Engineering with AI

Treat evaluation packages and data limits as their own capabilities; A green build does not verify output quality or authorization.

7. Main topic: From shared repository to testable boundaries

Synthesis in 30 seconds

  1. Sharing history facilitates coordinated changes, but does not create boundaries.
  2. The public interface and the rule of dependency make the limit observable.
  3. A gate produces evidence limited to its inputs, detector and version.

Objective

Reconstruct the chain producer → contract → consumer → gate and decide what evidence is missing in a specific change.

Mechanism and decisions

Two different decisions

The repository delimits history, revision and access to the code; The architectural border delimits knowledge between modules. A monorepo can contain independent applications with strict contracts; Multiple repositories can be coupled by a changing API. To choose structure, first record frequency of joint changes, permissions, tools and publication cycle. Then draw the allowed dependencies. The folder tree does not demonstrate that second decision.

Change of contract step by step

In the hypothetical example of a website that consumes @example/ui, the producer adds an optional property to Button. Before the change the public entry exports the previous button. The new version keeps the default value, modifies the exported type and tests both uses. The consumer who wants the variant updates his code; those who don't, maintain the behavior. The gate checks public imports, types, tests of both projects and build. The observed result depends on running those tests, not just saving both projects together.

Limits and recovery

An import to src/internal can compile today and break after an internal reorganization. Valid lint output does not prove the quality of the AI-generated summary; An evaluation fixture with criteria is needed, in addition to data authorization. If the graph omits a dynamic consumer, the affected test suite is incomplete: expand search by actual usage and run broader validation. When there is a false positive, log bounded exception with responsible and correction alternative.

Conditional comparison

The study by Jaspan and collaborators documents advantages of visibility, discovery and central management of dependencies in the studied environment, and advantages of flexibility, access control and stability for several repositories. It is evidence of commitments, not a universal rule. A team's decision must include tool maintenance costs and actual permits. Jaspan et al., Advantages and Disadvantages of a Monolithic Codebase (ICSE SEIP, 2018)

Worked example and verification

Given a Button change from mandatory prop label to optional prop title, consumers sending label stop compiling if it is removed without migration. Strategy: Accept both inputs temporarily, migrate uses, and retire the old one in a communicated version. Check by type and behavior test; if a consumer compiles using any, add actual usage test. Hypothetical example, not execution result.

Proposed reproducible check: creates a consumer who follows the contract and another who violates it; runs the relevant detector and compares outputs, including errors. The result of this session does not yet credit those executions.

Failure, alternative and production

Confusing shared history with secure integration; green type gate with cast to any; AI evaluation that uses the same case with which the instruction was designed and does not detect representative regressions.

In production documents owner, public input, failure signals and rollback path. A change detected by types does not replace execution tests; a static rule also does not demonstrate data properties or AI behavior.

7.1 Subtopic 1: Repositories and boundaries

Synthesis in 30 seconds

  1. The versioning unit determines how changes are coordinated.
  2. Separating repositories does not guarantee compatibility between versions.
  3. A monorepo does not imply differentiated permissions for sensitive code.

Objective

Choose code placement under access, coupling, and deployment restrictions.

Concepts of subtopic 1

Staff → Principal
Coordinated change: modification that requires reviewing producer and consumers to preserve a function

Example: the team updates client and service in the same revision when the error format changes.

Frontend Platform Architecture
Monorepo: a repository with shared history for multiple projects

Example: web and component package are versioned in the same revision.

Polyrepo: several repositories with history and revision cycles own

Example: the library publishes a version that the website adopts in another repository.

Logical border: usage rule between components independent of its physical location

Example: a package is accessible only by exports even if it shares the root folder with the web.

Product Engineering with AI
Data isolation: restricting data access based on need and permission

Example: an evaluator uses synthetic documents and cannot read production records.

Mechanism and decisions

Versions and coordination

In monorepo, a revision can update visible producers and consumers. In polyrepo, the producer publishes a version and each consumer modifies its dependency where appropriate. In both models the contract needs compatibility; Changing two files in a revision does not by itself preserve the behavior.

Access and border

If a team needs to prevent a developer from viewing a sensitive assembly, folder separation is not equivalent to repository permission. The data and secrets remain out of history. An organization can allow code visibility and limit access to operational data; it's a different decision.

Scenario-based selection

For applications that share types and change together weekly, a monorepo can reduce publishing steps. If teams need access controls or incompatible tools, separating repositories may be more sustainable. Measure cross-switch frequency and integration time before generalizing. Jaspan et al., Advantages and Disadvantages of a Monolithic Codebase (ICSE SEIP, 2018)

Worked example and verification

Web and SDK change an error field: in monorepo the same revision modifies both; SDK 2 is published in polyrepo and then the web is migrated. In both cases, a website still in SDK 1 needs compatibility or explicit transition.

Proposed reproducible check: creates a consumer who follows the contract and another who violates it; runs the relevant detector and compares outputs, including errors. The result of this session does not yet credit those executions.

Failure, alternative and production

Move code without a permissions plan and confuse “compile in my branch” with compatibility of deployed consumers.

In production documents owner, public input, failure signals and rollback path. A change detected by types does not replace execution tests; a static rule also does not demonstrate data properties or AI behavior.

7.2 Subtopic 2: Workspaces, applications and packages

Synthesis in 30 seconds

  1. Workspace registers local packages, it does not decide borders.
  2. An app deploys; a package exposes a reusable contract.
  3. Reuse requires API and ownership in addition to shared code.

Objective

Design entry points and detect imports that circumvent contracts.

Mechanism and decisions

Local resolution

npm workspaces register paths in the root package.json; during npm install it links local packages to resolve names. This reduces manual installation, but does not force the use of a public API or decide published versions. The consumer declares dependence; the package declares exports and types. npm Docs, Workspaces

Extraction criterion

Sharing a 10-line function does not always justify a package: you add version, contract, ownership, builds and tests. Extracts when the behavior and direction of change are actually shared. Keep the specifics of the experience in the application. Prevents a “common” package from ending up depending on applications.

Contract and failure

If the app imports src/private, an internal refactor breaks it. An exports field can block subpaths during resolution, but relative imports bypass that barrier; complemented with a limit rule. Try a public import that resolves and an internal one that fails. Change the implementation and check again. Hypothetical producer

Worked example and verification

package.json: {"name":"@example/ui","exports":{".":"./dist/index.js"},"types":"./dist/index.d.ts"}. The website depends on @example/ui. This presupposes build and emitted types: it is not enough to copy the manifest.

Proposed reproducible check: creates a consumer who follows the contract and another who violates it; runs the relevant detector and compares outputs, including errors. The result of this session does not yet credit those executions.

Failure, alternative and production

Circular package that consumes a web page; bundler alias that points to src and avoids exports; empty package created by convention only.

In production documents owner, public input, failure signals and rollback path. A change detected by types does not replace execution tests; a static rule also does not demonstrate data properties or AI behavior.

7.3 Subtopic 3: Graph and dependency management

Synthesis in 30 seconds

  1. Edges have direction: consumer points to provider.
  2. Cycles make it difficult to isolate and order changes.
  3. A static graph can omit dynamic use or deployment contracts.

Objective

Draw direct and transitive dependencies, find cycles, and select bounds tests. explicit.

Concepts of subtopic 3

Staff → Principal
Transitive impact: set of reachable consumers following dependencies

Example: a schema change affects the client and, through it, the two apps that import it.

Frontend Platform Architecture
Graph of projects: project nodes and edges of declared or detected dependency

Example: web → UI and panel → UI show direct consumers.

Cycle: dependency path that returns to the point of origin

Example: UI → web → UI prevents an acyclic build order.

Address rule: restriction on which layers can depend on others

Example: apps can consume packages; packages do not import apps.

Product Engineering with AI
Evaluation dependency: relationship between model change, data and cases to be reviewed

Example: a prompt change forces the summary set to be executed even if the website has not changed.

Mechanism and decisions

Reading the graph

A → B means A uses B. If Web → Client → Schema, changing Schema can affect Client and Web: the scope is obtained by reversing edges from the modified node. It is not equivalent to browsing providers from the Web; That answers another question. A project graph does not necessarily contain runtime calls or external dependencies.

Cycles and separation

If UI imports a Web helper while Web imports UI, there is a cycle. A pull to a shared package can break it only if the helper has independent responsibility; if not, move the responsibility to the correct owner. A layer rule encodes direction and the negative test attempts the forbidden edge. Nx, Explore your Workspace

Analysis confidence

Dynamic imports, code generation, configuration and consumption by URL may not appear. If the automated analysis cannot demonstrate coverage, run extensive validation and document the manual dependency. Changing an AI output scheme also runs behavioral evaluation cases.

Worked example and verification

Web Edges → Client, Panel → Client, Client → Scheme. Changing Scheme affects Client, Web and Panel as candidates. UI without edges to Scheme is not affected by that graph; completion requires checking for hidden dependencies.

Proposed reproducible check: creates a consumer who follows the contract and another who violates it; runs the relevant detector and compares outputs, including errors. The result of this session does not yet credit those executions.

Failure, alternative and production

Reverse direction and run only vendor tests; cycle that is “resolved” by ignoring the import; declare zero impact for an incomplete graph.

In production documents owner, public input, failure signals and rollback path. A change detected by types does not replace execution tests; a static rule also does not demonstrate data properties or AI behavior.

Exercises of subtopic 3

See reasoned solution

Web → Project-level UI can be translated into build:web which depends on build:ui. However lint:web does not have to depend on build:ui. The task graph has nodes per operation, with prerequisite edges; the orchestrator can parallelize nodes without dependencies. Nx, Run Tasks

Keys and outputs

A cache computes a key with sources, configuration, dependencies, and declared environment; if output exists for the same key, it reuses it. If the lockfile or a generator is omitted, stale output may serve. The cache does not validate semantics of an external model that changes outside the repository.

Affected strategy

After changing UI, execute UI build/tests and tasks of consuming apps that depend on that contract. A complete periodic validation captures graph omissions and changes in the environment. AI cases include fixtures, model version, and configuration as explicit inputs when they affect results.

Worked example and verification

Hypothetical tasks: build:ui → build:web; typecheck:web independent of build:ui if it reads source types. If the web bundle reads dist/ui, it does need the output of build:ui. The order depends on the files consumed, not the task name.

Proposed reproducible check: creates a consumer who follows the contract and another who violates it; runs the relevant detector and compares outputs, including errors. The result of this session does not yet credit those executions.

Failure, alternative and production

Cache ignoring build env; flagged task affected false by hidden dependency; gate that passes with previous artifact.

In production documents owner, public input, failure signals and rollback path. A change detected by types does not replace execution tests; a static rule also does not demonstrate data properties or AI behavior.

11. Production-ready example

External reference design, not validated or deployed. Hypothetical reservation system with apps/web scripts, packages/booking-client scripts, packages/booking-schema and reservation service. Web consumes only the client's public input; client defines request/response/error; The service authenticates, authorizes a resource and persists a reservation only once per idempotency key within its defined window. 

POST /reservations
Idempotency-Key: clave-generada-por-cliente
{ "slotId": "S-17", "customerId": "C-2" }

201 { "reservationId": "R-9", "status": "confirmed" }
409 { "code": "SLOT_TAKEN", "retryable": false }

Invariant: the same slot cannot be confirmed to two users. The key prevents duplicate retries of the same request, but does not replace a transactional constraint in the database for different requests. The service records correlation without sensitive data; the website shows accessible error with focus and message, and does not blindly retry 409. The client rejects unknown errors and shows safe recovery.

Build: schema and client are built before web if web reads their artifacts; A schema change executes service contract, client and consumers. Security: authorization lives on server; no credentials are saved in the repo. Deployment: extend contract, migrate clients, observe errors and remove fields in another delivery. Rollback: preserve compatibility during the return of the website or service. Tests needed: contract, concurrency with two requests, repeated idempotence, cross permissions, error accessibility, clean build and rollback. None of them were executed in this design.

Design operating contracts

Entry and authority. A hypothetical reservations scenario uses a server-authenticated session. The client only sends slotId and a random idempotent key; the server obtains the identity of the client from the session. The customerId field shown above illustrates the format of the initial example, but is not a source of authority: if it is accepted for compatibility, it is compared to the authenticated identity and any discrepancy is rejected. A malformed resource identifier receives 400; an absent session receives 401; a user without permission receives 403. Before recording observability details, personal data is deleted.

Status and concurrency. The reservation goes from requested to confirmed only after atomically inserting a row associated with an available slot. A single index onslot_id for committed rows protects the invariant even when two different requests compete. Within a transaction, the server queries an idempotency table for the identity and key combination. If it finds the same request, it returns the saved response; if the key appears with a different body, it responds 409 with a code other than SLOT_TAKEN. If it does not exist, it attempts the insert, persists the response, and commits. The transaction must define isolation and conflict treatment according to the chosen database; this pseudoflow does not by itself guarantee atomicity without a tested implementation. 

BEGIN;
-- La identidad proviene de la sesión; el hash une clave y cuerpo.
SELECT request_hash, status, response FROM idempotency
 WHERE actor_id = :actor AND key = :key FOR UPDATE;
-- Si existe y el hash coincide, responder con la respuesta registrada.
-- Si el hash difiere, rechazar el reuso de la clave.
INSERT INTO reservations (slot_id, actor_id, status)
 VALUES (:slot, :actor, 'confirmed');
-- Restricción única de slot confirmado: solo uno de dos INSERT gana.
INSERT INTO idempotency (actor_id, key, request_hash, status, response)
 VALUES (:actor, :key, :hash, 201, :response);
COMMIT;

Error states. The idempotency table requires a unique constraint on (actor_id, key). Two first requests with the same key may not see a previous row: one may fail to insert the key; after reversing its transaction, it queries again and retrieves the other's confirmed response, as long as the hash matches. A slot uniqueness violation caused by different keys becomes SLOT_TAKEN, not an unclassified 500. If the connection is interrupted after the commit and before the browser receives a response, the browser retries with the same key and the server returns the recorded response. If idempotence storage expires, the retention period and retry semantics must be documented; the unique index continues to protect the slot. 5xx responses support retry with backoff only under explicit rules and without revealing information about another user.

Check and operation. The proposed suite includes two simultaneous requests for the same slot, exact key repetition, key reuse with different body, cross access to another account, type error in the client, keyboard navigation and accessible error announcement. Records a correlation identifier, conflict rate, and errors per code without private content. In deployment, introduce supported fields and transactional protection first, then migrate clients and measure old responses, and only then remove fields. When faced with rollback, restore a binary compatible with both formats and preserve the uniqueness constraint.Status: Reference design not verified: No database, concurrency test, or deployment was run.

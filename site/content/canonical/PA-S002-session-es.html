Responsabilidad de cambio: asignación de quién evalúa el impacto de modificar un contrato

Ejemplo: el dueño del paquete UI consulta a sus aplicaciones consumidoras antes de retirar una exportación.

Cambio coordinado: modificación que requiere revisar productor y consumidores para conservar una función

Ejemplo: el equipo actualiza cliente y servicio en una misma revisión cuando cambia el formato de error.

Capacidad compartida: función con propietario y consumidores que justifica una unidad reutilizable

Ejemplo: un cliente de autenticación se extrae cuando web y panel usan el mismo contrato.

Impacto transitivo: conjunto de consumidores alcanzables siguiendo dependencias

Ejemplo: un cambio de esquema afecta al cliente y, por él, a las dos apps que lo importan.

Presupuesto de validación: decisión explícita sobre rapidez y riesgo de omisión

Ejemplo: un PR ejecuta tareas afectadas y la rama principal ejecuta suite completa.

Política de ingeniería: regla con propósito, detector, consecuencia y dueño

Ejemplo: el acuerdo prohíbe imports a src y asigna revisión a plataforma.

Excepción temporal: desviación con causa, alcance, dueño y revisión

Ejemplo: un consumidor legado conserva un import hasta migrar su dependencia.

Plan de compatibilidad: secuencia acordada para ampliar, migrar y retirar un contrato

Ejemplo: un owner publica alias temporal y registra consumidores antes de retirar un campo.

Ownership: responsabilidad explícita de revisar y mantener un contrato

Ejemplo: el equipo de plataforma responde a cambios del paquete de UI.

ADR: registro breve de contexto, opciones, decisión y consecuencias

Ejemplo: un ADR explica por qué se limita el import interno y cuándo revisar la regla.

Deprecación: proceso comunicado para retirar una capacidad tras migrar consumidores

Ejemplo: una exportación antigua anuncia reemplazo y fecha de revisión.

Frontera arquitectónica: restricción sobre las dependencias permitidas entre componentes

Ejemplo: una aplicación importa un componente desde la entrada publicada del paquete, nunca desde src/internal.

Contrato público: entradas y comportamientos prometidos a los consumidores

Ejemplo: @ejemplo/ui exporta Button y su tipo de propiedades desde su punto de entrada.

Monorepo: un repositorio con historia compartida para varios proyectos

Ejemplo: web y paquete de componentes se versionan en la misma revisión.

Polyrepo: varios repositorios con historial y ciclos de revisión propios

Ejemplo: la biblioteca publica una versión que la web adopta en otro repositorio.

Frontera lógica: regla de uso entre componentes independiente de su ubicación física

Ejemplo: un paquete es accesible solo por exports aunque comparta carpeta raíz con la web.

Workspace: proyecto local registrado en la configuración de un gestor de paquetes

Ejemplo: npm enlaza el paquete @ejemplo/ui cuando figura en workspaces.

Aplicación: unidad desplegable que compone capacidades para usuarios

Ejemplo: la web crea páginas y consume un paquete de UI.

Paquete: unidad nombrada con dependencias y puntos de entrada

Ejemplo: @ejemplo/ui publica su índice y tipos sin exponer directorios internos.

Import profundo: importación que evita el punto de entrada declarado

Ejemplo: la web accede a @ejemplo/ui/src/private en vez de @ejemplo/ui.

Grafo de proyectos: nodos de proyectos y aristas de dependencia declarada o detectada

Ejemplo: web → UI y panel → UI muestran consumidores directos.

Ciclo: ruta de dependencias que vuelve al punto de origen

Ejemplo: UI → web → UI impide un orden acíclico de construcción.

Regla de dirección: restricción sobre qué capas pueden depender de otras

Ejemplo: apps pueden consumir packages; packages no importan apps.

Grafo de tareas: relaciones de prerrequisito entre operaciones concretas

Ejemplo: build:web depende de build:ui y typecheck:web.

Entrada de caché: archivo, entorno o configuración cuyo valor influye en la salida

Ejemplo: versión del compilador y lockfile participan en la clave de build.

Salida de tarea: artefacto o estado producido por una operación

Ejemplo: build:ui genera JS y declaraciones de tipos consumidas por la web.

Gate de CI: condición ejecutada automáticamente antes de integrar cambios

Ejemplo: format, lint, tipos, pruebas y build reportan estados independientes.

Prueba negativa: ensayo que demuestra que el detector falla ante un incumplimiento

Ejemplo: añadir un import interno en fixture debe producir exit distinto de cero.

API pública: superficie admitida de un paquete para sus consumidores

Ejemplo: el índice exporta Button sin exponer su archivo de render interno.

Compatibilidad semántica: conservación del significado que los consumidores esperan

Ejemplo: un campo status sigue representando estados del mismo dominio tras un refactor.

Migración de consumidores: transición trazable de usos antiguos a una API admitida

Ejemplo: la web cambia import relativo por @ejemplo/ui y se prueba la pantalla.

Ingeniería de Producto con IA
Contrato de datos: forma, significado y permisos acordados para un intercambio de información

Ejemplo: el cliente de resúmenes recibe texto autorizado y devuelve un resultado validado con error tipado.

Evaluación de comportamiento: prueba con casos y criterios para detectar cambios de calidad no captados por el compilador

Ejemplo: un conjunto fijo de documentos compara la presencia de citas al cambiar la instrucción de resumen.

Aislamiento de datos: restricción de acceso a datos según necesidad y permiso

Ejemplo: un evaluador usa documentos sintéticos y no puede leer expedientes de producción.

Paquete de evaluación: conjunto versionado de casos, criterios y runner para una capacidad de IA

Ejemplo: fixtures de documentos y aserciones de citas se mantienen separados de la UI.

Dependencia de evaluación: relación entre cambio de modelo, datos y casos que deben revisarse

Ejemplo: un cambio de prompt obliga a ejecutar el conjunto de resumen aunque la web no haya cambiado.

Fixture de evaluación: caso estable con entrada y criterio esperado

Ejemplo: un documento sintético exige citas válidas en la respuesta del resumen.

Gate de evaluación: criterio basado en casos y calidad observables de una función de IA

Ejemplo: una suite de documentos sintéticos comprueba que las respuestas incluyan citas verificables.

Validación de esquema: comprobación estructural y semántica de datos en una frontera

Ejemplo: el cliente rechaza un JSON sin id y texto antes de renderizar.

Autorización de datos: comprobación de que el actor puede usar la información concreta

Ejemplo: el servidor filtra documentos por tenant antes de enviarlos a un modelo.

Regresión de comportamiento: cambio observable en calidad o seguridad pese a interfaces estables

Ejemplo: al cambiar modelo, resúmenes omiten fuentes aunque el JSON conserve su forma.

Gobernanza de evaluación: asignación de quién mantiene fixtures, umbrales y revisión de fallos

Ejemplo: el dueño del resumen revisa ejemplos cuando cambia modelo o prompt.

7. Tema principal: Del repositorio compartido a límites comprobables

Síntesis en 30 segundos

  1. Compartir historial facilita cambios coordinados, pero no crea fronteras.
  2. La interfaz pública y la regla de dependencia hacen observable el límite.
  3. Un gate produce evidencia limitada a sus entradas, detector y versión.

Objetivo

Reconstruir la cadena productor → contrato → consumidor → gate y decidir qué evidencia falta en un cambio concreto.

Mecanismo y decisiones

Dos decisiones diferentes

El repositorio delimita historia, revisión y acceso al código; la frontera arquitectónica delimita conocimiento entre módulos. Un monorepo puede contener aplicaciones independientes con contratos estrictos; varios repositorios pueden acoplarse por una API cambiante. Para elegir estructura primero registra frecuencia de cambios conjuntos, permisos, herramientas y ciclo de publicación. Después dibuja las dependencias permitidas. El árbol de carpetas no demuestra esa segunda decisión.

Cambio de contrato paso a paso

En el ejemplo hipotético de una web que consume @ejemplo/ui, el productor añade una propiedad opcional a Button. Antes del cambio la entrada pública exporta el botón anterior. La versión nueva conserva el valor por defecto, modifica el tipo exportado y prueba ambos usos. El consumidor que quiere la variante actualiza su código; el que no, mantiene el comportamiento. El gate verifica imports públicos, tipos, tests de ambos proyectos y build. El resultado observado depende de ejecutar esas pruebas, no del solo hecho de guardar ambos proyectos juntos.

Límites y recuperación

Un import a src/internal puede compilar hoy y romper tras una reorganización interna. Una salida válida de lint no prueba la calidad del resumen generado por IA; se necesita un fixture de evaluación con criterios, además de autorización de datos. Si el grafo omite un consumidor dinámico, el conjunto de pruebas afectadas está incompleto: ampliar búsqueda por uso real y ejecutar validación más amplia. Cuando hay un falso positivo, registrar excepción acotada con responsable y alternativa de corrección.

Comparación condicionada

El estudio de Jaspan y colaboradores documenta ventajas de visibilidad, descubrimiento y gestión central de dependencias en el entorno estudiado, y ventajas de flexibilidad, control de acceso y estabilidad para varios repositorios. Es evidencia de compromisos, no una regla universal. La decisión de un equipo debe incluir costo de mantenimiento de herramientas y permisos reales. Jaspan et al., Advantages and Disadvantages of a Monolithic Codebase (ICSE SEIP, 2018)

Ejemplo resuelto y verificación

Dado un cambio de Button de prop obligatoria label a prop opcional title, los consumidores que enviaban label dejan de compilar si se retira sin migración. Estrategia: aceptar ambas entradas temporalmente, migrar usos y retirar la anterior en una versión comunicada. Verificar por tipo y prueba de comportamiento; si un consumidor compila mediante any, agregar prueba de uso real. Ejemplo hipotético, no resultado de ejecución.

Comprobación reproducible propuesta: crea un consumidor que siga el contrato y otro que lo viole; ejecuta el detector relevante y compara salidas, incluidos errores. El resultado de esta sesión todavía no acredita esas ejecuciones.

Fallo, alternativa y producción

Confundir historial compartido con integración segura; gate de tipos verde con cast a any; evaluación de IA que usa el mismo caso con el que se diseñó la instrucción y no detecta regresiones representativas.

En producción documenta propietario, entrada pública, señales de fallo y camino de reversión. Un cambio detectado por tipos no reemplaza pruebas de ejecución; una regla estática tampoco demuestra propiedades de datos o conducta de IA.

7.1 Subtema 1: Repositorios y fronteras

Síntesis en 30 segundos

  1. La unidad de versionado determina cómo se coordinan cambios.
  2. Separar repositorios no garantiza compatibilidad entre versiones.
  3. Un monorepo no implica permisos diferenciados para código sensible.

Elegir ubicación del código bajo restricciones de acceso, acoplamiento y despliegue.

Mecanismo y decisiones

Versiones y coordinación

En monorepo, una revisión puede actualizar productor y consumidores visibles. En polyrepo, el productor publica una versión y cada consumidor modifica su dependencia cuando corresponda. En ambos modelos el contrato necesita compatibilidad; cambiar dos archivos en una revisión no conserva por sí solo el comportamiento.

Acceso y frontera

Si un equipo necesita impedir que un desarrollador vea un conjunto sensible, la separación por carpetas no es equivalente a permiso de repositorio. Los datos y secretos siguen fuera del historial. Una organización puede permitir visibilidad de código y limitar acceso a datos operativos; es una decisión distinta.

Selección basada en escenario

Para aplicaciones que comparten tipos y cambian juntas semanalmente, un monorepo puede reducir pasos de publicación. Si equipos necesitan controles de acceso o herramientas incompatibles, separar repositorios puede ser más sostenible. Medir frecuencia de cambios cruzados y tiempo de integración antes de generalizar. Jaspan et al., Advantages and Disadvantages of a Monolithic Codebase (ICSE SEIP, 2018)

Ejemplo resuelto y verificación

Web y SDK cambian un campo de error: en monorepo la misma revisión modifica ambos; en polyrepo se publica SDK 2 y luego se migra web. En los dos casos una web aún en SDK 1 necesita compatibilidad o transición explícita.

Fallo, alternativa y producción

Mover código sin plan de permisos y confundir “compila en mi rama” con compatibilidad de consumidores desplegados.

En producción documenta propietario, entrada pública, señales de fallo y camino de reversión. Un cambio detectado por tipos no reemplaza pruebas de ejecución; una regla estática tampoco demuestra propiedades de datos o conducta de IA.

El requisito de acceso. Evaluar repositorio separado o mecanismo demostrado de control de acceso. Una carpeta en el mismo repo no aporta ese permiso.

Síntesis en 30 segundos

  1. Aristas tienen dirección: consumidor apunta al proveedor.

Mecanismo y decisiones

Lectura del grafo

A → B significa que A usa B. Si Web → Cliente → Esquema, cambiar Esquema puede afectar Cliente y Web: el alcance se obtiene invirtiendo aristas desde el nodo modificado. No equivale a recorrer proveedores desde Web; eso responde otra pregunta. Un grafo de proyecto no contiene necesariamente llamadas de runtime ni dependencias externas.

Ciclos y separación

Si UI importa un helper de Web mientras Web importa UI, hay ciclo. Una extracción a package compartido puede romperlo solo si el helper tiene responsabilidad independiente; si no, mueve la responsabilidad al dueño correcto. Una regla de capas codifica dirección y la prueba negativa intenta la arista prohibida. Nx, Explore your Workspace

Imports dinámicos, generación de código, configuración y consumo por URL pueden no aparecer. Si el análisis automático no puede demostrar cobertura, ejecuta una validación amplia y documenta la dependencia manual. Al cambiar un esquema de salida de IA también corre los casos de evaluación de comportamiento.

11. Ejemplo listo para producción

Diseño de referencia externo, no validado ni desplegado. Sistema hipotético de reservas con apps/web, packages/booking-client, packages/booking-schema y servicio de reservas. Web consume solo la entrada pública del cliente; el cliente define request/response/error; el servicio autentica, autoriza recurso y persiste una reserva una sola vez por clave de idempotencia dentro de su ventana definida. 

POST /reservations
Idempotency-Key: clave-generada-por-cliente
{ "slotId": "S-17", "customerId": "C-2" }

201 { "reservationId": "R-9", "status": "confirmed" }
409 { "code": "SLOT_TAKEN", "retryable": false }

Invariante: un mismo slot no puede confirmarse a dos usuarios. La clave evita duplicar reintentos de la misma solicitud, pero no sustituye una restricción transaccional en la base de datos para solicitudes distintas. El servicio registra correlación sin datos sensibles; la web muestra error accesible con foco y mensaje, y no reintenta 409 ciegamente. El cliente rechaza errores desconocidos y muestra recuperación segura.

Build: esquema y cliente se construyen antes que web si la web lee sus artefactos; un cambio de esquema ejecuta contrato de servicio, cliente y consumidores. Seguridad: la autorización vive en servidor; no se guardan credenciales en el repo. Despliegue: ampliar contrato, migrar clientes, observar errores y retirar campos en otra entrega. Rollback: conservar compatibilidad durante el retorno de web o servicio. Pruebas necesarias: contrato, concurrencia con dos solicitudes, idempotencia repetida, permisos cruzados, accesibilidad de error, build limpio y reversión. Ninguna de ellas se ejecutó en este diseño.

Contratos operativos del diseño

Entrada y autoridad. Un escenario hipotético de reservas usa una sesión autenticada por el servidor. El cliente solo envía slotId y una clave aleatoria de idempotencia; el servidor obtiene la identidad del cliente de la sesión. El campo customerId mostrado antes ilustra el formato del ejemplo inicial, pero no es fuente de autoridad: si se acepta por compatibilidad, se compara con la identidad autenticada y se rechaza toda discrepancia. Un identificador de recurso malformado recibe 400; una sesión ausente recibe 401; un usuario sin permiso recibe 403. Antes de registrar detalles de observabilidad se eliminan datos personales.

Estado y concurrencia. La reserva pasa de solicitada a confirmada solo después de insertar atómicamente una fila asociada a un slot disponible. Un índice único sobre slot_id para filas confirmadas protege la invariante aun cuando dos peticiones distintas compitan. Dentro de una transacción, el servidor consulta una tabla de idempotencia por la combinación de identidad y clave. Si encuentra la misma petición, devuelve la respuesta guardada; si la clave aparece con un cuerpo distinto, responde 409 con un código distinto de SLOT_TAKEN. Si no existe, intenta la inserción, persiste la respuesta y confirma. La transacción debe definir aislamiento y tratamiento del conflicto según la base de datos elegida; este pseudoflujo no garantiza por sí mismo atomicidad sin una implementación probada. 

BEGIN;
-- La identidad proviene de la sesión; el hash une clave y cuerpo.
SELECT request_hash, status, response FROM idempotency
 WHERE actor_id = :actor AND key = :key FOR UPDATE;
-- Si existe y el hash coincide, responder con la respuesta registrada.
-- Si el hash difiere, rechazar el reuso de la clave.
INSERT INTO reservations (slot_id, actor_id, status)
 VALUES (:slot, :actor, 'confirmed');
-- Restricción única de slot confirmado: solo uno de dos INSERT gana.
INSERT INTO idempotency (actor_id, key, request_hash, status, response)
 VALUES (:actor, :key, :hash, 201, :response);
COMMIT;

Estados de error. La tabla de idempotencia requiere una restricción única sobre (actor_id, key). Dos primeras solicitudes con la misma clave pueden no ver una fila previa: una puede fallar al insertar la clave; tras revertir su transacción, consulta de nuevo y recupera la respuesta confirmada de la otra, siempre que el hash coincida. Una violación de unicidad sobre el slot causada por claves distintas se convierte en SLOT_TAKEN, no en un 500 sin clasificación. Si la conexión se interrumpe después del commit y antes de que el navegador reciba respuesta, este reintenta con la misma clave y el servidor devuelve la respuesta registrada. Si el almacenamiento de idempotencia expira, el periodo de retención y la semántica de reintento deben documentarse; el índice único sigue protegiendo el slot. Las respuestas 5xx admiten reintento con backoff solo bajo reglas explícitas y sin revelar información de otro usuario.

Comprobación y operación. La suite propuesta incluye dos peticiones simultáneas para el mismo slot, repetición exacta de clave, reutilización de clave con cuerpo diferente, acceso cruzado a otra cuenta, error tipado en el cliente, navegación con teclado y anuncio accesible de error. Registra un identificador de correlación, tasa de conflictos y errores por código sin contenido privado. En despliegue, introducir primero los campos compatibles y la protección transaccional, después migrar clientes y medir respuestas antiguas, y solo entonces retirar campos. Ante rollback, restaurar un binario compatible con ambos formatos y conservar la restricción de unicidad. Estado: diseño de referencia no verificado: no se ejecutó base de datos, prueba de concurrencia ni despliegue.

13. Ejercicios

  1. Comprensión: Dos apps viven en un repo y una importa packages/ui/src/internal. Identifica unidad de versionado, frontera y prueba.
    Solución Monorepo es unidad; la frontera se evade. Declara API pública, prueba que uso válido pasa y el interno falla.

    Solución Por aristas inversas, Cliente, Web y Panel son candidatos afectados. Confirmar imports dinámicos y contratos de despliegue.

    Criterio La positiva resuelve por entrada pública; la negativa falla por regla específica sin excluir carpeta.
  4. Decisión: Un proyecto exige permisos separados y cambio conjunto diario. Compara opciones con riesgos.
    Solución Primero valida el requisito de acceso. Polyrepo con contrato/versiones es candidato; monorepo solo si mecanismo real de permiso satisface restricción.
  5. Liderazgo: Un gate falla en código legado y el owner propone desactivarlo.
    Solución Acota excepción a usos identificados, asigna dueño/plazo, define API o migración, prueba negativa vigente para código nuevo y revisión de impacto.
